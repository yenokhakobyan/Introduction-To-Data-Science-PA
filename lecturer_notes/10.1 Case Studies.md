## Case 1: Predicting Customer Churn in Telecom

**Problem Context:**
You work for a telecom provider experiencing 15% monthly churn rate. The business goal is to identify customers likely to churn within 30 days so the retention team can intervene. Available data includes customer demographics, usage patterns, billing history, and support interactions over the past 12 months. The model needs to be interpretable for the business team and run daily batch predictions.

**Question:** What model would you use to predict churn? How would you handle categorical variables and evaluate the model given the business constraints?

**Answer:**

**Solution Strategy:** This is a supervised binary classification problem where we need to balance predictive accuracy with interpretability. The 30-day prediction window gives us a clear target definition, and the need for interpretability suggests starting with simpler models before exploring complex ones.

**Type of Learning:** Supervised learning because we have historical data with known churn outcomes (customers who canceled their service).

**Model Choice:** I'd start with Logistic Regression for baseline interpretability, then test Random Forest and XGBoost. Random Forest provides good feature importance insights while XGBoost often achieves superior performance on tabular data.

**Feature Engineering:** One-hot encode categorical variables like contract type and payment method. Create recency features (days since last payment, last support call). Engineer interaction terms between tenure and monthly charges. Handle missing values in optional services with a separate "unknown" category. Scale numerical features for logistic regression.

**Model Evaluation:** Primary metric would be AUC-ROC for ranking performance, but also focus on precision at different recall levels since false positives are costly (unnecessary retention offers). Use stratified k-fold cross-validation to handle class imbalance.

**Optimization Strategy:** Grid search on key hyperparameters (C for logistic regression, max_depth and n_estimators for tree models). Apply SMOTE for class balancing but validate on original distribution. Use early stopping for XGBoost to prevent overfitting.

**Challenges & Pitfalls:** Class imbalance requires careful sampling strategies. Potential data leakage from features that occur after churn decision. Concept drift as customer behavior changes over time. Overfitting on minority class leading to poor generalization.

**Communication to Stakeholders:** "Our model identifies 70% of churning customers with 40% precision, meaning 4 out of 10 retention calls reach someone actually planning to leave. Top predictors are contract type, recent usage decline, and support call frequency. This allows targeting 1,000 high-risk customers monthly instead of 10,000 random ones."

## Case 2: Fraud Detection in Credit Card Transactions

**Problem Context:**
A financial institution processes millions of credit card transactions daily with a fraud rate of 0.1%. The business needs real-time fraud detection with decisions made within 100ms. False positives are extremely costly (blocked legitimate transactions), but false negatives allow financial losses. Historical transaction data includes amount, merchant, location, time, and customer profiles.

**Question:** How would you design a fraud detection system that operates in real-time while minimizing false positives?

**Answer:**

**Solution Strategy:** This is an extremely imbalanced classification problem requiring real-time inference. We need a two-stage approach: a fast screening model for real-time decisions and a more complex model for post-transaction analysis.

**Type of Learning:** Supervised learning with extreme class imbalance (0.1% fraud rate). Consider unsupervised anomaly detection as a complement to identify new fraud patterns.

**Model Choice:** Primary model: Logistic Regression or lightweight Random Forest for real-time inference. Secondary model: XGBoost or Neural Network for batch analysis. Consider Isolation Forest for anomaly detection on new fraud patterns.

**Feature Engineering:** Create velocity features (transactions per hour, spending in last 24h). Geographic features (distance from home, unusual location). Time-based features (hour of day, day of week). Customer behavior features (deviation from typical spending patterns). Use feature hashing for categorical variables to handle new merchants.

**Model Evaluation:** Primary metric is precision at high recall (minimize false positives). Use precision-recall curves rather than ROC. Implement time-based splits for validation (train on historical, test on recent data). Monitor performance separately for different transaction types.

**Optimization Strategy:** Use class weights heavily favoring the fraud class. Implement ensemble of models trained on different balanced samples. Use threshold optimization to find optimal precision-recall trade-off. Consider cost-sensitive learning.

**Challenges & Pitfalls:** Extreme class imbalance makes standard metrics misleading. Fraudsters adapt quickly, causing concept drift. Real-time latency constraints limit model complexity. Data leakage from future information. Adversarial attacks from fraudsters.

**Communication to Stakeholders:** "Our system catches 80% of fraud attempts while only blocking 1 in 1,000 legitimate transactions. We save $10M annually in fraud losses with $2M in customer friction costs. The model flags unusual spending patterns, new locations, and velocity spikes as key fraud indicators."

## Case 3: Demand Forecasting for E-commerce Inventory

**Problem Context:**
An e-commerce company manages inventory for 50,000 products across multiple warehouses. The goal is to predict demand for the next 30 days to optimize inventory levels. Stockouts cost sales while overstock ties up capital. Data includes historical sales, prices, promotions, seasonality, and external factors like weather and holidays.

**Question:** What approach would you use for demand forecasting across thousands of products with different seasonality patterns?

**Answer:**

**Solution Strategy:** This is a time series forecasting problem with multiple products requiring different modeling approaches. Some products have clear seasonal patterns while others are more random. We need a scalable solution that can handle both high-volume and low-volume products.

**Type of Learning:** Supervised learning treating this as a regression problem with time-based features. For products with insufficient history, use unsupervised clustering to group similar products.

**Model Choice:** Hierarchical approach: Prophet or ARIMA for products with clear seasonality, XGBoost with time features for products with complex patterns, and simple moving averages for low-volume products. Consider ensemble methods combining multiple approaches.

**Feature Engineering:** Create lag features (sales 1, 7, 30 days ago), rolling window statistics (mean, std over different periods), seasonality indicators (day of week, month, holiday flags). Price elasticity features (price changes, competitor pricing). Promotion indicators and their interaction with seasonality.

**Model Evaluation:** Primary metrics are MAE and MAPE for business interpretability. Use time-based cross-validation with walk-forward validation. Evaluate separately for different product categories and volume tiers. Track forecast accuracy at different horizons (1-day, 7-day, 30-day).

**Optimization Strategy:** Grid search on seasonal parameters for Prophet. For XGBoost, tune tree depth and learning rate. Use different models for different product categories. Implement ensemble weighting based on recent performance.

**Challenges & Pitfalls:** Cold start problem for new products. Intermittent demand patterns for low-volume items. Promotion effects difficult to model. External shocks (viral products, supply disruptions) not captured in historical data. Computational scalability for 50,000 products.

**Communication to Stakeholders:** "Our forecasting system reduces stockouts by 25% while cutting excess inventory by 15%. We achieve 85% accuracy for high-volume products and 70% for low-volume items. The model automatically adjusts for seasonal patterns, promotions, and holidays, updating predictions daily as new sales data arrives."

## Case 4: Content Recommendation System for Streaming Platform

**Problem Context:**
A video streaming platform wants to improve user engagement by recommending relevant content. The platform has 100M users and 50K titles with rich metadata (genre, actors, ratings). User behavior includes viewing history, ratings, search queries, and engagement metrics (watch time, completion rate). The goal is to increase average watch time per user.

**Question:** How would you design a recommendation system that balances personalization with content diversity?

**Answer:**

**Solution Strategy:** This requires a hybrid recommendation approach combining collaborative filtering (user-item interactions) with content-based filtering (item features). We need to handle both the cold start problem and ensure recommendation diversity to avoid filter bubbles.

**Type of Learning:** Combination of supervised and unsupervised learning. Supervised for predicting user ratings/engagement, unsupervised for user clustering and content similarity.

**Model Choice:** Matrix factorization (SVD, NMF) for collaborative filtering, content-based similarity using cosine similarity on item features, and deep learning (neural collaborative filtering) for complex interactions. Implement ensemble combining multiple approaches.

**Feature Engineering:** User features: viewing history embeddings, genre preferences, time-of-day patterns, device usage. Item features: genre vectors, cast/director embeddings, content metadata, popularity scores. Interaction features: user-item engagement signals, temporal patterns, context (weekend vs weekday).

**Model Evaluation:** Primary metrics are precision@K, recall@K, and NDCG for ranking quality. Business metrics include watch time increase, user retention, and content diversity (coverage of catalog). Use temporal splits for validation (train on historical, test on recent interactions).

**Optimization Strategy:** Hyperparameter tuning for factorization dimensions and regularization. A/B testing for different recommendation strategies. Use negative sampling for implicit feedback. Implement real-time learning for user preference updates.

**Challenges & Pitfalls:** Cold start for new users and content. Popularity bias favoring mainstream content. Filter bubbles reducing discovery. Scalability for real-time recommendations. Concept drift as user preferences change.

**Communication to Stakeholders:** "Our recommendation system increases average watch time by 20% and user retention by 15%. We serve personalized recommendations in under 50ms while ensuring users discover content across 80% of our catalog. The system learns from 1 billion daily interactions to continuously improve suggestions."

## Case 5: Medical Diagnosis from Patient Symptoms

**Problem Context:**
A healthcare system wants to develop a diagnostic support tool for primary care physicians. The system should suggest possible diagnoses based on patient symptoms, medical history, and basic test results. The dataset includes anonymized patient records with symptoms, diagnoses, and outcomes. The system must be highly interpretable and conservative (prefer false positives over false negatives).

**Question:** How would you approach building a diagnostic support system that provides explainable recommendations while maintaining high sensitivity?

**Answer:**

**Solution Strategy:** This is a multi-label classification problem where patient symptoms map to multiple potential diagnoses. Given the medical context, interpretability and high sensitivity are crucial. We need a system that can explain its reasoning and errs on the side of caution.

**Type of Learning:** Supervised learning with multi-label classification. Each patient can have multiple diagnoses, and the model should predict probability distributions over possible conditions.

**Model Choice:** Decision Trees or Random Forest for interpretability, with Logistic Regression as baseline. Consider using separate binary classifiers for each diagnosis category. Avoid black-box models like neural networks unless explainability can be ensured through techniques like SHAP.

**Feature Engineering:** Symptom encoding (binary indicators, severity scores), demographic features (age, gender), medical history features (previous diagnoses, medications), test result features (blood work, vital signs). Create interaction terms between related symptoms.

**Model Evaluation:** Primary focus on sensitivity (recall) to avoid missing diagnoses. Use precision-recall curves for each diagnosis category. Implement stratified cross-validation by patient demographics. Use area under precision-recall curve (AUPRC) for imbalanced diagnoses.

**Optimization Strategy:** Threshold optimization to achieve desired sensitivity levels. Use class weights to penalize false negatives more heavily. Implement ensemble methods with majority voting. Consider cost-sensitive learning with higher costs for missing serious conditions.

**Challenges & Pitfalls:** Rare disease detection with limited training data. Symptom overlap between conditions. Bias in training data (certain demographics underrepresented). Liability concerns with false negatives. Integration with existing clinical workflows.

**Communication to Stakeholders:** "Our diagnostic support system identifies 95% of serious conditions while flagging 30% of cases for further investigation. The system explains its reasoning using patient symptoms and medical history, helping physicians make informed decisions. It serves as a safety net, not a replacement for clinical judgment."

Lag features capturing temporal dependencies. Equipment-specific features (age, maintenance history, operating conditions). Deviation from normal operating parameters.

**Model Evaluation:** Primary metric is F1-score balancing precision and recall. Use precision-recall curves to find optimal threshold. Implement time-based cross-validation respecting temporal order. Evaluate prediction accuracy at different time horizons (7, 14, 30 days).

**Optimization Strategy:** Grid search on LSTM architecture (layers, units, dropout). For XGBoost, tune tree parameters and learning rate. Use early stopping to prevent overfitting. Implement online learning to adapt to new failure patterns.

**Challenges & Pitfalls:** Imbalanced data (few failures vs normal operation). Sensor noise and missing data. Different failure modes requiring different models. Concept drift as equipment ages. False alarms causing maintenance fatigue.

**Communication to Stakeholders:** "Our predictive maintenance system reduces unplanned downtime by 40% while cutting maintenance costs by 25%.
