### Understanding Databases: Setting the Stage

Before diving into SQL syntax, help students grasp why databases exist. A database is like a well-organized filing cabinet where information is stored in a structured way that makes it easy to find, update, and analyze. SQLite is particularly valuable for learning because it removes the complexity of server setup while providing all the essential SQL features.

Think of SQLite as a single-file database engine. Unlike traditional database systems that require separate server installations, SQLite stores everything in one file. This makes it perfect for learning, prototyping, and small to medium-sized applications. Major applications like Firefox, Android, and iOS use SQLite internally.

### SQLite's Unique Characteristics

SQLite uses what we call "dynamic typing," which is different from most database systems. While other databases enforce strict data types, SQLite is more flexible. This flexibility can be both helpful and potentially confusing for students, so it's important to explain how SQLite interprets and stores data.

When you declare a column as INTEGER in SQLite, you're expressing a preference rather than a rigid requirement. SQLite will try to store data as an integer when possible, but it won't reject a text value. This concept of "type affinity" is unique to SQLite and worth exploring with examples.

## Chapter 2: Data Definition Language (DDL) - Building Your Database Structure

### Creating Tables: The Foundation of Your Database

Creating tables is like designing the blueprint of a building. Each table represents an entity in your real-world scenario, and each column represents an attribute of that entity. Let's start with a practical example that students can relate to: a university database system.

```sql
-- Our first table: Students
-- Notice how we think about what information we need to store
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY AUTOINCREMENT,  -- Unique identifier, auto-generated
    first_name TEXT NOT NULL,                      -- Required field
    last_name TEXT NOT NULL,                       -- Required field
    email TEXT UNIQUE NOT NULL,                    -- Must be unique across all students
    date_of_birth DATE,                           -- Optional field
    enrollment_date DATE DEFAULT (date('now')),    -- Automatically set to current date
    major TEXT,                                   -- Can be NULL initially
    gpa REAL CHECK (gpa >= 0.0 AND gpa <= 4.0)   -- Constrained to valid GPA range
);
```

### Understanding Primary Keys: The Foundation of Data Integrity

A primary key is like a social security number for each row in your table. It must be unique and cannot be NULL. The AUTOINCREMENT keyword tells SQLite to automatically generate sequential numbers, which is convenient for creating unique identifiers without worrying about duplicates.

Explain to students that primary keys serve two crucial purposes: they ensure each row can be uniquely identified, and they create an implicit index that makes queries faster. This is why queries that search by primary key are typically very fast.

### Constraints: Enforcing Business Rules

Constraints are like rules that protect your data quality. They prevent invalid data from entering your database. Let's explore each type of constraint with real-world reasoning:

```sql
-- A comprehensive example showing various constraints
CREATE TABLE courses (
    course_id INTEGER PRIMARY KEY,
    course_code TEXT NOT NULL UNIQUE,              -- Must exist and be unique (e.g., "CS101")
    course_name TEXT NOT NULL,                     -- Required course title
    credits INTEGER NOT NULL CHECK (credits > 0 AND credits <= 6),  -- Reasonable credit range
    department TEXT NOT NULL,                      -- Which department offers this course
    prerequisites TEXT,                            -- Optional, comma-separated course codes
    max_enrollment INTEGER DEFAULT 30 CHECK (max_enrollment > 0),  -- Default class size
    is_active BOOLEAN DEFAULT 1                    -- Whether course is currently offered
);
```

The CHECK constraint is particularly powerful because it allows you to encode business logic directly into your database structure. For example, ensuring that credits are between 1 and 6 prevents data entry errors that could cause problems later.

### Foreign Keys: Connecting Your Tables

Foreign keys are like bridges between tables. They ensure that relationships between tables remain consistent. Think of them as preventing "orphaned" records where a student enrollment might reference a course that doesn't exist.

```sql
-- Enable foreign key support (crucial in SQLite)
PRAGMA foreign_keys = ON;

-- Create the enrollment table that connects students and courses
CREATE TABLE enrollments (
    enrollment_id INTEGER PRIMARY KEY AUTOINCREMENT,
    student_id INTEGER NOT NULL,
    course_id INTEGER NOT NULL,
    semester TEXT NOT NULL,                        -- e.g., "Fall 2024"
    enrollment_date DATE DEFAULT (date('now')),
    grade TEXT CHECK (grade IN ('A', 'B', 'C', 'D', 'F', 'W', 'I')),
    
    -- Foreign key constraints with different deletion behaviors
    FOREIGN KEY (student_id) REFERENCES students(student_id) ON DELETE CASCADE,
    FOREIGN KEY (course_id) REFERENCES courses(course_id) ON DELETE RESTRICT,
    
    -- Ensure a student can't enroll in the same course twice in the same semester
    UNIQUE (student_id, course_id, semester)
);
```

Understanding ON DELETE options is crucial. CASCADE means "if the referenced record is deleted, delete this record too." RESTRICT means "prevent deletion of the referenced record if it's being used here." These choices depend on your business logic and data retention requirements.

```sql
INSERT INTO students (first_name, last_name, email, major, gpa)
```

### SELECT: The Foundation of Data Retrieval - A Complete Step-by-Step Guide

The SELECT statement is truly the cornerstone of SQL, and understanding it deeply will transform how you think about data. Think of SELECT as your conversation with the database, where you're asking specific questions and the database responds with exactly the information you need. Just as you might ask a librarian increasingly specific questions about books, you can ask your database increasingly sophisticated questions about your data.

Let's build your SELECT skills methodically, starting with the simplest concepts and progressing to advanced techniques that will make you a confident data analyst. Each step builds on the previous one, so take time to understand each concept before moving forward.

#### Step 1: Understanding the Basic SELECT Structure

Every SELECT statement follows a logical pattern, much like asking a question in English. When you ask someone "What are the names and ages of all the students in the computer science class?", you're naturally structuring your question with what you want to know, from where, and any conditions. SQL follows this same intuitive pattern.

```sql
-- The most basic SELECT: show me everything from a table
-- Think of this as saying "Show me everything you know about students"
SELECT * FROM students;

-- The asterisk (*) is a wildcard meaning "all columns"
-- This is like asking "Tell me everything about every student"
-- Use this for exploration, but avoid in production code for performance reasons
```

When you run this query, you're asking the database to retrieve every piece of information it stores about every student. The asterisk acts as a shortcut, but as you become more sophisticated in your data work, you'll want to be more specific about exactly what information you need.

```sql
-- Being selective: choose only the columns you need
-- This is like asking "Just tell me the names and GPAs of all students"
SELECT first_name, last_name, gpa FROM students;

-- Column order in your SELECT determines display order
-- You control how information is presented
SELECT gpa, last_name, first_name FROM students;  -- GPA appears first now

-- You can create calculated columns and give them meaningful names
-- This shows the power of SQL to do more than just retrieve stored data
SELECT 
    first_name,
    last_name,
    gpa,
    gpa * 25 AS gpa_percentage,  -- Convert 4.0 scale to percentage
    'Student' AS record_type     -- Add a literal value to every row
FROM students;
```

Notice how we're starting to manipulate and enhance our data during retrieval. This is one of SQL's great strengths – you don't just get back exactly what was stored; you can transform and enhance it to meet your specific needs.

#### Step 2: Adding Conditions with WHERE - Filtering Your Results

The WHERE clause is where SQL becomes truly powerful for analysis. Think of WHERE as applying a filter to your data, like using a search function to find only the items that meet your specific criteria. This is equivalent to saying "Of all the students, show me only those who meet these specific conditions."

```sql
-- Simple WHERE condition: find students with high GPAs
-- This asks: "Which students have a GPA of 3.5 or higher?"
SELECT first_name, last_name, gpa
FROM students
WHERE gpa >= 3.5;

-- Multiple conditions with AND: both conditions must be true
-- This asks: "Which computer science students have high GPAs?"
SELECT first_name, last_name, major, gpa
FROM students
WHERE gpa >= 3.5 AND major = 'Computer Science';

-- Multiple conditions with OR: either condition can be true
-- This asks: "Which students are either honor students OR in computer science?"
SELECT first_name, last_name, major, gpa
FROM students
WHERE gpa >= 3.5 OR major = 'Computer Science';

-- Using parentheses to control logic (like mathematical operations)
-- This asks: "Which students are in STEM fields AND have good grades?"
SELECT first_name, last_name, major, gpa
FROM students
WHERE (major = 'Computer Science' OR major = 'Mathematics' OR major = 'Physics')
    AND gpa >= 3.0;
```

Understanding the logical operators deeply will help you ask precisely the right questions of your data. Notice how parentheses work just like in mathematics, controlling the order of operations and ensuring your logic is evaluated correctly.

#### Step 3: Working with Text Data - Pattern Matching and String Functions

Text data requires special handling because you're often looking for patterns rather than exact matches. Think about how you might search for books in a library catalog – you might remember part of a title or an author's last name, but not the complete, exact text.

```sql
-- LIKE operator for pattern matching
-- % means "any number of characters (including zero)"
-- _ means "exactly one character"

-- Find students whose last name starts with 'S'
SELECT first_name, last_name, email
FROM students
WHERE last_name LIKE 'S%';

-- Find students with university email addresses
-- This is useful for distinguishing students from staff or external users
SELECT first_name, last_name, email
FROM students
WHERE email LIKE '%@university.edu';

-- Find students whose first name has exactly 4 letters and starts with 'J'
-- The underscores represent exactly 3 more characters after 'J'
SELECT first_name, last_name
FROM students
WHERE first_name LIKE 'J___';

-- Case-insensitive searching (important for user-friendly applications)
-- SQLite is case-insensitive by default, but this makes it explicit
SELECT first_name, last_name, major
FROM students
WHERE LOWER(major) LIKE '%computer%'  -- Finds "Computer Science", "computer engineering", etc.
    OR LOWER(major) LIKE '%engineering%';

-- Complex pattern matching for data validation
-- Find potentially invalid email addresses
SELECT first_name, last_name, email
FROM students
WHERE email NOT LIKE '%@%.%'  -- Must contain @ followed later by a dot
    OR email LIKE '%..%'       -- Should not contain consecutive dots
    OR LENGTH(email) < 5;      -- Should be at least 5 characters long
```

Pattern matching is incredibly powerful for data analysis and cleaning. You can find inconsistencies, validate data formats, and search for information even when you don't know the exact text you're looking for.

#### Step 4: Handling Missing Data - The NULL Challenge

NULL values represent missing or unknown information, and they require special handling that often confuses beginners. Think of NULL not as "zero" or "empty," but as "we don't know what goes here." This distinction is crucial for accurate data analysis.

```sql
-- Finding records with missing information
-- IS NULL checks for missing values
SELECT first_name, last_name, major, gpa
FROM students
WHERE major IS NULL;  -- Students who haven't declared a major yet

-- Finding records with known information
-- IS NOT NULL checks for present values
SELECT first_name, last_name, major, gpa
FROM students
WHERE major IS NOT NULL AND gpa IS NOT NULL;

-- COMMON MISTAKE: Never use = or != with NULL
-- This will NOT work as expected:
-- SELECT * FROM students WHERE major = NULL;    -- Wrong!
-- SELECT * FROM students WHERE major != NULL;   -- Wrong!

-- Handling NULL values in calculations and comparisons
-- NULL in any calculation makes the entire result NULL
SELECT 
    first_name,
    last_name,
    gpa,
    -- Use COALESCE to provide default values for NULL
    COALESCE(gpa, 0.0) AS gpa_with_default,
    -- Use CASE for more complex NULL handling logic
    CASE 
        WHEN gpa IS NULL THEN 'No GPA recorded'
        WHEN gpa >= 3.5 THEN 'Honor Student'
        WHEN gpa >= 3.0 THEN 'Good Standing'
        ELSE 'Needs Improvement'
    END AS academic_status
FROM students;

-- Combining NULL checks with other conditions
-- Find students who either have no major declared OR are in Computer Science
SELECT first_name, last_name, major
FROM students
WHERE major IS NULL OR major = 'Computer Science';
```

Understanding NULL behavior is essential for accurate data analysis. Many data quality issues stem from improper NULL handling, so developing strong habits here will serve you well throughout your career.

#### Step 5: Sorting Your Results - ORDER BY Fundamentals

Sorting transforms raw data into meaningful information by organizing it in ways that reveal patterns and insights. Think about how organizing books alphabetically by author makes them easier to find, or how sorting students by GPA immediately shows you who the top performers are.

```sql
-- Basic sorting: single column, ascending (lowest to highest)
-- ASC is the default, so you can omit it
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa;  -- Same as ORDER BY gpa ASC

-- Descending sort: highest to lowest
-- Great for finding top performers or identifying outliers
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC;

-- Multi-column sorting: primary and secondary sort criteria
-- This creates a hierarchy: sort by major first, then by GPA within each major
SELECT first_name, last_name, major, gpa
FROM students
ORDER BY major ASC, gpa DESC;  -- Major A-Z, then highest GPA first within each major

-- Sorting with calculated values
-- You can sort by expressions, not just stored column values
SELECT 
    first_name,
    last_name,
    gpa,
    LENGTH(first_name) + LENGTH(last_name) AS name_length
FROM students
ORDER BY name_length DESC, last_name ASC;

-- Handling NULL values in sorting
-- NULLs typically appear first in ascending sorts, last in descending sorts
-- You can control this behavior explicitly
SELECT first_name, last_name, major, gpa
FROM students
ORDER BY gpa DESC NULLS LAST;  -- Put students with no GPA at the end

-- Complex sorting with CASE expressions
-- Create custom sort orders that match business logic
SELECT first_name, last_name, major, gpa
FROM students
ORDER BY 
    CASE major
        WHEN 'Computer Science' THEN 1    -- CS students first
        WHEN 'Mathematics' THEN 2         -- Math students second
        WHEN 'Physics' THEN 3            -- Physics students third
        ELSE 4                           -- All other majors last
    END,
    gpa DESC;  -- Within each major group, sort by GPA
```

Thoughtful sorting can transform a confusing mass of data into clear, actionable insights. The order in which you present information significantly affects how people interpret and use it.

#### Step 6: Limiting and Sampling Your Results

When working with large datasets, you often need to focus on subsets of your data rather than overwhelming yourself (or your application) with too much information at once. Think of this like reading the first few pages of several books to decide which one interests you most.

```sql
-- LIMIT: Get just the top N records
-- Perfect for "top 10 lists" or pagination in applications
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC
LIMIT 10;  -- Top 10 students by GPA

-- LIMIT with OFFSET: Skip some records, then take others
-- This is how pagination works in web applications
SELECT first_name, last_name, gpa
FROM students
ORDER BY gpa DESC
LIMIT 10 OFFSET 20;  -- Skip first 20, then take next 10 (records 21-30)

-- Combining everything: complex filtering, sorting, and limiting
-- "Who are the top 5 Computer Science students by GPA?"
SELECT first_name, last_name, major, gpa
FROM students
WHERE major = 'Computer Science' 
    AND gpa IS NOT NULL
ORDER BY gpa DESC
LIMIT 5;

-- Sampling techniques for data exploration
-- Get a random sample to understand your data without processing everything
SELECT first_name, last_name, major, gpa
FROM students
WHERE major IS NOT NULL
ORDER BY RANDOM()  -- SQLite-specific function for random ordering
LIMIT 100;  -- Random sample of 100 students

-- Finding outliers: both highest and lowest values
-- This technique helps identify data quality issues or exceptional cases
SELECT 'Highest GPA' AS category, first_name, last_name, gpa
FROM students
WHERE gpa IS NOT NULL
ORDER BY gpa DESC
LIMIT 5

UNION ALL  -- Combine results from multiple queries

SELECT 'Lowest GPA' AS category, first_name, last_name, gpa
FROM students
WHERE gpa IS NOT NULL
ORDER BY gpa ASC
LIMIT 5;
```

Limiting results is not just about performance; it's about focusing your analysis on the most relevant information and avoiding information overload.

#### Step 7: Advanced Filtering Techniques

As your questions become more sophisticated, you'll need more advanced filtering techniques. These methods allow you to ask complex questions that go beyond simple equality checks.

```sql
-- Range queries: finding values between limits
-- Much more readable than multiple AND conditions
SELECT first_name, last_name, gpa
FROM students
WHERE gpa BETWEEN 3.0 AND 3.5;  -- Same as: gpa >= 3.0 AND gpa <= 3.5

-- Set membership: checking if a value matches any in a list
-- More efficient and readable than multiple OR conditions
SELECT first_name, last_name, major
FROM students
WHERE major IN ('Computer Science', 'Mathematics', 'Physics', 'Engineering');

-- Negation: finding records that DON'T match criteria
-- Useful for data cleaning and identifying exceptions
SELECT first_name, last_name, major, email
FROM students
WHERE major NOT IN ('Computer Science', 'Mathematics')
    AND email NOT LIKE '%@university.edu';

-- Date and time filtering (crucial for real-world applications)
-- Assuming we have enrollment_date column
SELECT first_name, last_name, enrollment_date
FROM students
WHERE enrollment_date >= date('2024-01-01')  -- Students enrolled this year
    AND enrollment_date < date('2025-01-01');

-- Complex conditions with subqueries (preview of advanced topics)
-- "Find students whose GPA is above the average"
SELECT first_name, last_name, gpa
FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students WHERE gpa IS NOT NULL);

-- Regular expressions for advanced pattern matching
-- SQLite supports GLOB for shell-style wildcards
SELECT first_name, last_name, email
FROM students
WHERE email GLOB '*[0-9]*@university.edu';  -- Email contains numbers before @university.edu
```

These advanced filtering techniques allow you to ask increasingly sophisticated questions of your data, moving from simple lookups to complex analytical queries.

#### Step 8: Calculated Fields and Data Transformation

One of SQL's greatest strengths is its ability to transform and enhance data during retrieval. Instead of just getting back what was stored, you can calculate new values, format data for presentation, and create insights that weren't explicitly stored in the database.

```sql
-- Mathematical calculations
-- Transform stored data into more useful formats
SELECT 
    first_name,
    last_name,
    gpa,
    gpa * 25 AS gpa_percentage,           -- Convert to percentage
    4.0 - gpa AS points_below_perfect,    -- How far from perfect GPA
    ROUND(gpa, 1) AS gpa_rounded         -- Round to one decimal place
FROM students
WHERE gpa IS NOT NULL;

-- String manipulation and formatting
-- Clean and standardize text data for better presentation
SELECT 
    UPPER(first_name) AS first_name_caps,
    LOWER(last_name) AS last_name_lower,
    first_name || ' ' || last_name AS full_name,  -- Concatenation
    LENGTH(first_name || last_name) AS name_length,
    SUBSTR(email, 1, INSTR(email, '@') - 1) AS username,  -- Extract username from email
    'Student ID: ' || student_id AS formatted_id
FROM students;

-- Conditional logic with CASE expressions
-- Create categories and classifications based on stored data
SELECT 
    first_name,
    last_name,
    gpa,
    CASE 
        WHEN gpa >= 3.8 THEN 'Summa Cum Laude'
        WHEN gpa >= 3.6 THEN 'Magna Cum Laude'
        WHEN gpa >= 3.4 THEN 'Cum Laude'
        WHEN gpa >= 2.0 THEN 'Good Standing'
        ELSE 'Academic Probation'
    END AS academic_honor,
    CASE 
        WHEN major IS NULL THEN 'Undeclared'
        WHEN major IN ('Computer Science', 'Mathematics', 'Physics') THEN 'STEM'
        WHEN major IN ('English', 'History', 'Philosophy') THEN 'Liberal Arts'
        ELSE 'Other'
    END AS division
FROM students;

-- Date calculations (assuming we have date columns)
-- Extract meaningful information from date fields
SELECT 
    first_name,
    last_name,
    enrollment_date,
    date('now') AS today,
    julianday('now') - julianday(enrollment_date) AS days_enrolled,
    CAST((julianday('now') - julianday(enrollment_date)) / 365.25 AS INTEGER) AS years_enrolled,
    strftime('%Y', enrollment_date) AS enrollment_year,
    strftime('%m', enrollment_date) AS enrollment_month
FROM students
WHERE enrollment_date IS NOT NULL;

-- Complex transformations combining multiple techniques
-- Create rich, analytical views of your data
SELECT 
    student_id,
    UPPER(SUBSTR(first_name, 1, 1)) || LOWER(SUBSTR(first_name, 2)) AS first_name_proper,
    UPPER(SUBSTR(last_name, 1, 1)) || LOWER(SUBSTR(last_name, 2)) AS last_name_proper,
    CASE 
        WHEN gpa IS NULL THEN 'No GPA on record'
        WHEN gpa >= 3.5 THEN 'Honor Student (' || ROUND(gpa, 2) || ')'
        ELSE 'Regular Student (' || ROUND(gpa, 2) || ')'
    END AS student_status,
    COALESCE(major, 'Undeclared') AS major_display,
    LENGTH(COALESCE(major, 'Undeclared')) AS major_name_length
FROM students;
```

These calculated fields transform your database from a simple storage system into a powerful analytical engine. You're not limited to what was originally stored; you can derive new insights and create exactly the view of your data that you need.

#### Step 9: Putting It All Together - Complex SELECT Examples

Now let's combine all these techniques into sophisticated queries that demonstrate the full power of SELECT statements. These examples show how the individual pieces work together to answer complex business questions.

```sql
-- Complex query combining multiple techniques
-- "Find the top 10 STEM students by GPA, showing their academic status and contact info"
SELECT 
    ROW_NUMBER() OVER (ORDER BY gpa DESC) AS rank,
    first_name || ' ' || last_name AS full_name,
    major,
    ROUND(gpa, 2) AS gpa_rounded,
    CASE 
        WHEN gpa >= 3.8 THEN 'Summa Cum Laude'
        WHEN gpa >= 3.6 THEN 'Magna Cum Laude'
        WHEN gpa >= 3.4 THEN 'Cum Laude'
        ELSE 'Honor Roll'
    END AS honors,
    email,
    CAST((julianday('now') - julianday(enrollment_date)) / 365.25 AS INTEGER) AS years_enrolled
FROM students
WHERE major IN ('Computer Science', 'Mathematics', 'Physics', 'Engineering')
    AND gpa IS NOT NULL
    AND gpa >= 3.0  -- Only students in good standing
ORDER BY gpa DESC, last_name ASC
LIMIT 10;

-- Data quality analysis query
-- "Identify potential data quality issues in our student records"
SELECT 
    'Missing Major' AS issue_type,
    COUNT(*) AS record_count,
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM students), 2) AS percentage
FROM students
WHERE major IS NULL

UNION ALL

SELECT 
    'Missing GPA' AS issue_type,
    COUNT(*) AS record_count,
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM students), 2) AS percentage
FROM students
WHERE gpa IS NULL

UNION ALL

SELECT 
    'Invalid Email Format' AS issue_type,
    COUNT(*) AS record_count,
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM students), 2) AS percentage
FROM students
WHERE email NOT LIKE '%@%.%' OR email LIKE '%..%'

UNION ALL

SELECT 
    'Unusual GPA Values' AS issue_type,
    COUNT(*) AS record_count,
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*) FROM students), 2) AS percentage
FROM students
WHERE gpa < 0.0 OR gpa > 4.0;

-- Analytical query for decision making
-- "Analyze student performance by major to identify programs that might need support"
SELECT 
    COALESCE(major, 'Undeclared') AS major_name,
    COUNT(*) AS total_students,
    COUNT(CASE WHEN gpa IS NOT NULL THEN 1 END) AS students_with_gpa,
    ROUND(AVG(gpa), 2) AS avg_gpa,
    MIN(gpa) AS min_gpa,
    MAX(gpa) AS max_gpa,
    COUNT(CASE WHEN gpa >= 3.5 THEN 1 END) AS honor_students,
    COUNT(CASE WHEN gpa < 2.0 THEN 1 END) AS students_at_risk,
    ROUND(
        COUNT(CASE WHEN gpa >= 3.5 THEN 1 END) * 100.0 / 
        COUNT(CASE WHEN gpa IS NOT NULL THEN 1 END), 1
    ) AS honor_percentage
FROM students
GROUP BY major
HAVING COUNT(*) >= 5  -- Only majors with at least 5 students
ORDER BY avg_gpa DESC;
```

#### Mental Models and Common Patterns

As you practice writing SELECT statements, develop these mental models to help you think through complex queries:

**The Funnel Approach**: Start with all your data, then progressively filter it down using WHERE clauses until you have exactly the records you need. Then use SELECT to choose which columns to display and how to transform them.

**The Question Framework**: Before writing any query, ask yourself these questions in order:
1. What data do I need to see? (SELECT clause)
2. Where is that data stored? (FROM clause)  
3. What conditions must be met? (WHERE clause)
4. How should the results be organized? (ORDER BY clause)
5. Do I need all results or just some? (LIMIT clause)

**The Transformation Pipeline**: Think of SELECT as a data transformation pipeline where raw stored data goes through a series of filters, calculations, and formatting steps to become exactly the information you need.

Remember that becoming proficient with SELECT statements is like learning a new language. Start with simple sentences (queries) and gradually work up to complex expressions. Practice regularly with real data, and don't be afraid to experiment. The more you practice asking different questions of your data, the more intuitive these patterns will become.

The key insight is that SELECT is not just about retrieving data; it's about transforming raw information into actionable insights. Master these fundamentals, and you'll have the foundation for all advanced SQL techniques that follow.

### Aggregate Functions: Summarizing Your Data

Aggregate functions help you ask questions like "How many?" "What's the average?" and "What's the total?" These are essential for data analysis and reporting.

```sql
-- Basic aggregates
SELECT 
    COUNT(*) as total_students,
    COUNT(major) as students_with_declared_major,  -- COUNT ignores NULL values
    AVG(gpa) as average_gpa,
    MIN(gpa) as lowest_gpa,
    MAX(gpa) as highest_gpa
FROM students;

-- GROUP BY: Breaking down aggregates by categories
SELECT 
    major,
    COUNT(*) as student_count,
    AVG(gpa) as avg_gpa,
    MIN(gpa) as min_gpa,
    MAX(gpa) as max_gpa
FROM students
WHERE major IS NOT NULL
GROUP BY major
ORDER BY avg_gpa DESC;

-- HAVING: Filtering groups (like WHERE but for aggregated data)
SELECT 
    major,
    COUNT(*) as student_count,
    AVG(gpa) as avg_gpa
FROM students
WHERE major IS NOT NULL
GROUP BY major
HAVING COUNT(*) >= 5  -- Only show majors with 5 or more students
ORDER BY avg_gpa DESC;
```

### JOINs: Combining Data from Multiple Tables

JOINs are perhaps the most powerful feature of relational databases. They allow you to combine related information from different tables, which is essential for answering complex questions about your data.

```sql
-- INNER JOIN: Get students and their enrollments (only students who are enrolled)
SELECT 
    s.first_name,
    s.last_name,
    c.course_code,
    c.course_name,
    e.semester,
    e.grade
FROM students s
INNER JOIN enrollments e ON s.student_id = e.student_id
INNER JOIN courses c ON e.course_id = c.course_id
```

## Chapter 4: Advanced Query Techniques

### Subqueries: Queries Within Queries

Subqueries are like asking a question within a question. They're powerful tools for complex data analysis and can often make complicated problems much simpler to solve.

```sql
-- Find students with above-average GPA
SELECT first_name, last_name, gpa
FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students WHERE gpa IS NOT NULL)
ORDER BY gpa DESC;

-- Find students enrolled in the most popular course
SELECT s.first_name, s.last_name
FROM students s
WHERE s.student_id IN (
    SELECT e.student_id
    FROM enrollments e
    WHERE e.course_id = (
        -- First, find the course with the most enrollments
        SELECT course_id
        FROM enrollments
        GROUP BY course_id
        ORDER BY COUNT(*) DESC
        LIMIT 1
    )
);

-- Correlated subquery: Students with above-average GPA for their major
SELECT first_name, last_name, major, gpa
FROM students s1
WHERE gpa > (
    SELECT AVG(gpa)
    FROM students s2
    WHERE s2.major = s1.major
    AND s2.gpa IS NOT NULL
)
ORDER BY major, gpa DESC;
```

### Window Functions: Advanced Analytics

Window functions allow you to perform calculations across sets of rows that relate to the current row. They're incredibly powerful for ranking, running totals, and comparative analysis.

```sql
-- Rank students by GPA within each major
SELECT 
    first_name,
    last_name,
    major,
    gpa,
    RANK() OVER (PARTITION BY major ORDER BY gpa DESC) as major_rank,
    DENSE_RANK() OVER (ORDER BY gpa DESC) as overall_rank
FROM students
WHERE major IS NOT NULL AND gpa IS NOT NULL;

-- Running total of enrollments by semester
SELECT 
    semester,
    COUNT(*) as semester_enrollments,
    SUM(COUNT(*)) OVER (ORDER BY semester) as cumulative_enrollments
FROM enrollments
GROUP BY semester
ORDER BY semester;

-- Compare each student's GPA to their major average
SELECT 
    first_name,
    last_name,
    major,
    gpa,
    AVG(gpa) OVER (PARTITION BY major) as major_avg_gpa,
    gpa - AVG(gpa) OVER (PARTITION BY major) as gpa_vs_major_avg
FROM students
WHERE major IS NOT NULL AND gpa IS NOT NULL
ORDER BY major, gpa DESC;
```

### Common Table Expressions (CTEs): Organizing Complex Queries

CTEs help you break down complex queries into more readable, manageable pieces. Think of them as creating temporary named result sets that you can reference in your main query.

```sql
-- Using CTE to find students who have improved their grades over time
WITH grade_points AS (
    SELECT 
        student_id,
        semester,
        AVG(CASE grade 
            WHEN 'A' THEN 4.0 
            WHEN 'B' THEN 3.0 
            WHEN 'C' THEN 2.0 
            WHEN 'D' THEN 1.0 
            WHEN 'F' THEN 0.0 
        END) as semester_gpa
    FROM enrollments
    WHERE grade IN ('A', 'B', 'C', 'D', 'F')
    GROUP BY student_id, semester
),
gpa_trends AS (
    SELECT 
        student_id,
        semester,
        semester_gpa,
        LAG(semester_gpa) OVER (PARTITION BY student_id ORDER BY semester) as previous_gpa
    FROM grade_points
)
SELECT 
    s.first_name,
    s.last_name,
    gt.semester,
    gt.semester_gpa,
    gt.previous_gpa,
    gt.semester_gpa - gt.previous_gpa as gpa_change
FROM students s
JOIN gpa_trends gt ON s.student_id = gt.student_id
WHERE gt.previous_gpa IS NOT NULL
AND gt.semester_gpa > gt.previous_gpa
ORDER BY gpa_change DESC;
```

## Chapter 6: Advanced Constraints and Data Integrity

Understanding constraints deeply is like learning the rules that govern a well-functioning society. Just as laws prevent chaos and ensure fairness, database constraints prevent data corruption and maintain consistency. Let's explore the sophisticated ways SQLite allows you to protect and validate your data.

### Advanced CHECK Constraints: Encoding Complex Business Rules

CHECK constraints go far beyond simple range validation. They can enforce complex business logic directly at the database level, which means your data stays consistent regardless of which application or user interacts with it. Think of CHECK constraints as your database's built-in quality control system.

```sql
-- Complex CHECK constraint with multiple conditions and functions
CREATE TABLE employees (
    employee_id INTEGER PRIMARY KEY AUTOINCREMENT,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE,
    hire_date DATE NOT NULL,
    birth_date DATE NOT NULL,
    salary REAL NOT NULL,
    department TEXT NOT NULL,
    manager_id INTEGER,
    
    -- Age verification: must be at least 16 to work, calculated from birth_date
    CHECK (
        (julianday('now') - julianday(birth_date)) / 365.25 >= 16
    ),
    
    -- Hire date cannot be in the future or before company founding (1995)
    CHECK (
        hire_date <= date('now') AND 
        hire_date >= '1995-01-01'
    ),
    
    -- Email must follow basic email pattern and match company domain
    CHECK (
        email LIKE '%@company.com' AND
        email NOT LIKE '%..%' AND  -- No consecutive dots
        length(email) >= 7  -- Minimum reasonable email length
    ),
    
    -- Salary ranges based on department (encoding pay scales)
    CHECK (
        (department = 'Intern' AND salary BETWEEN 15000 AND 25000) OR
        (department = 'Junior' AND salary BETWEEN 40000 AND 65000) OR
        (department = 'Senior' AND salary BETWEEN 65000 AND 120000) OR
        (department = 'Management' AND salary BETWEEN 80000 AND 200000) OR
        (department = 'Executive' AND salary BETWEEN 150000 AND 500000)
    ),
    
    -- Managers must be from management or executive departments
    CHECK (
        manager_id IS NULL OR 
        manager_id IN (
            SELECT employee_id FROM employees 
            WHERE department IN ('Management', 'Executive')
        )
    ),
    
    -- Self-reference prevention: an employee cannot be their own manager
    CHECK (employee_id != manager_id),
    
    FOREIGN KEY (manager_id) REFERENCES employees(employee_id) ON DELETE SET NULL
);
```

Notice how these constraints work together to create a comprehensive data validation system. The age calculation using Julian day functions ensures we're working with actual dates, not just text that looks like dates. The email validation goes beyond just requiring an @ symbol to enforce company standards and prevent common formatting errors.

### Multi-Column Constraints: Relationships Between Fields

Sometimes business rules involve relationships between multiple columns. These constraints help ensure that combinations of data make logical sense together.

```sql
-- Project management table with complex multi-column constraints
CREATE TABLE projects (
    project_id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_name TEXT NOT NULL,
    start_date DATE NOT NULL,
    planned_end_date DATE NOT NULL,
    actual_end_date DATE,
    budget REAL NOT NULL,
    spent_amount REAL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'Planning',
    priority TEXT NOT NULL DEFAULT 'Medium',
    project_manager_id INTEGER NOT NULL,
    
    -- Logical date relationships
    CHECK (planned_end_date > start_date),  -- Project must have positive duration
    CHECK (actual_end_date IS NULL OR actual_end_date >= start_date),  -- Can't end before starting
    
    -- Budget constraints
    CHECK (budget > 0),  -- Projects must have positive budgets
    CHECK (spent_amount >= 0),  -- Can't spend negative money
    CHECK (spent_amount <= budget * 1.1),  -- Allow 10% budget overrun but not more
    
    -- Status transitions follow business logic
    CHECK (
        status IN ('Planning', 'Active', 'On Hold', 'Completed', 'Cancelled')
    ),
    
    -- Priority levels
    CHECK (
        priority IN ('Low', 'Medium', 'High', 'Critical')
    ),
    
    -- Complex business rule: completed projects must have actual end date and full status consistency
    CHECK (
        (status = 'Completed' AND actual_end_date IS NOT NULL) OR
        (status != 'Completed')
    ),
    
    -- Critical projects must have high budgets (business rule example)
    CHECK (
        (priority = 'Critical' AND budget >= 100000) OR
        (priority != 'Critical')
    ),
    
    FOREIGN KEY (project_manager_id) REFERENCES employees(employee_id) ON DELETE RESTRICT
);
```

### Table-Level Constraints: Ensuring Data Consistency Across Rows

Table-level constraints can reference multiple columns and even perform subqueries to ensure complex business rules are followed across your entire dataset.

```sql
-- Course scheduling table with sophisticated constraint logic
CREATE TABLE course_schedules (
    schedule_id INTEGER PRIMARY KEY AUTOINCREMENT,
    course_id INTEGER NOT NULL,
    instructor_id INTEGER NOT NULL,
    room_number TEXT NOT NULL,
    building TEXT NOT NULL,
    day_of_week TEXT NOT NULL,
    start_time TIME NOT NULL,
    end_time TIME NOT NULL,
    semester TEXT NOT NULL,
    max_capacity INTEGER NOT NULL,
    
    -- Basic validation constraints
    CHECK (day_of_week IN ('Monday', 'Tuesday', 'Wednesday', 'Thursday', 'Friday', 'Saturday', 'Sunday')),
    CHECK (start_time < end_time),  -- Class must have positive duration
    CHECK (max_capacity > 0 AND max_capacity <= 500),  -- Reasonable class sizes
    
    -- Semester format validation (e.g., "Fall 2024", "Spring 2025")
    CHECK (
        semester GLOB '[A-Z]*[0-9][0-9][0-9][0-9]' AND
        (semester LIKE 'Fall %' OR semester LIKE 'Spring %' OR semester LIKE 'Summer %')
    ),
    
    -- Time slot validation (classes should start and end at reasonable times)
    CHECK (
        start_time BETWEEN '07:00' AND '21:00' AND
        end_time BETWEEN '08:00' AND '22:00'
    ),
    
    -- Lunch break consideration: no classes should span the typical lunch hour
    CHECK (
        NOT (start_time < '12:00' AND end_time > '13:00') OR
        (start_time >= '13:00' OR end_time <= '12:00')
    ),
    
    -- Unique constraint preventing double-booking of rooms
    UNIQUE (room_number, building, day_of_week, start_time, semester),
    
    -- Unique constraint preventing instructors from being double-booked
    UNIQUE (instructor_id, day_of_week, start_time, semester),
    
    FOREIGN KEY (course_id) REFERENCES courses(course_id) ON DELETE CASCADE,
    FOREIGN KEY (instructor_id) REFERENCES employees(employee_id) ON DELETE RESTRICT
);
```

### Cascading Actions: Managing Data Relationships Automatically

When you have foreign key relationships, you need to decide what happens when referenced data changes or gets deleted. These cascading actions automate data maintenance and help preserve referential integrity. Think of them as automated housekeeping rules that maintain consistency when changes occur.

```sql
-- Comprehensive example showing different cascading strategies
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY AUTOINCREMENT,
    company_name TEXT NOT NULL,
    contact_email TEXT NOT NULL UNIQUE,
    created_date DATE DEFAULT (date('now')),
    status TEXT DEFAULT 'Active' CHECK (status IN ('Active', 'Inactive', 'Suspended'))
);

CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INTEGER NOT NULL,
    order_date DATE DEFAULT (date('now')),
    total_amount REAL NOT NULL CHECK (total_amount >= 0),
    status TEXT DEFAULT 'Pending' CHECK (status IN ('Pending', 'Processing', 'Shipped', 'Delivered', 'Cancelled')),
    
    -- When customer is deleted, we want to keep order history for business records
    -- but set customer_id to NULL and mark the relationship as broken
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE SET NULL
);

CREATE TABLE order_items (
    item_id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id INTEGER NOT NULL,
    product_name TEXT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price REAL NOT NULL CHECK (unit_price >= 0),
    
    -- When an order is deleted, all its items should also be deleted
    -- This maintains referential integrity and prevents orphaned records
    FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE
);

CREATE TABLE order_payments (
    payment_id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id INTEGER NOT NULL,
    payment_date DATE DEFAULT (date('now')),
    amount REAL NOT NULL CHECK (amount > 0),
    payment_method TEXT NOT NULL,
    
    -- Prevent deletion of orders that have payments recorded
    -- This preserves financial audit trails
    FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE RESTRICT
);

-- Audit trail table that should never lose its references
CREATE TABLE order_audit_log (
    audit_id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id INTEGER NOT NULL,
    action TEXT NOT NULL,
    timestamp DATETIME DEFAULT (datetime('now')),
    user_id TEXT,
    
    -- When order is deleted, prevent deletion to maintain audit trail
    FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE RESTRICT
);
```

Understanding the different cascading options helps you make intelligent decisions about data relationships. CASCADE means "delete this too when the parent is deleted," which is perfect for dependent data like order items. SET NULL preserves the record but removes the broken reference, useful for maintaining historical data. RESTRICT prevents deletion entirely, which is crucial for maintaining audit trails and financial records.

### Conditional Constraints Using CASE Expressions

Sometimes your business rules are more complex than simple yes/no validations. SQLite allows you to use CASE expressions within CHECK constraints to implement conditional logic that adapts based on other field values.

```sql
-- Employee benefits table with conditional eligibility rules
CREATE TABLE employee_benefits (
    benefit_id INTEGER PRIMARY KEY AUTOINCREMENT,
    employee_id INTEGER NOT NULL,
    benefit_type TEXT NOT NULL,
    coverage_level TEXT NOT NULL,
    monthly_cost REAL NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE,
    
    -- Benefit type validation
    CHECK (benefit_type IN ('Health', 'Dental', 'Vision', 'Life', 'Disability', 'Retirement')),
    
    -- Coverage levels vary by benefit type
    CHECK (
        CASE benefit_type
            WHEN 'Health' THEN coverage_level IN ('Basic', 'Standard', 'Premium', 'Family')
            WHEN 'Dental' THEN coverage_level IN ('Basic', 'Standard')
            WHEN 'Vision' THEN coverage_level IN ('Basic', 'Standard')
            WHEN 'Life' THEN coverage_level IN ('1x Salary', '2x Salary', '3x Salary')
            WHEN 'Disability' THEN coverage_level IN ('Short-term', 'Long-term', 'Both')
            WHEN 'Retirement' THEN coverage_level IN ('3% Match', '5% Match', '7% Match')
            ELSE 0  -- Invalid benefit type
        END
    ),
    
    -- Cost validation based on benefit type and coverage
    CHECK (
        monthly_cost >= 
        CASE 
            WHEN benefit_type = 'Health' AND coverage_level = 'Basic' THEN 150
            WHEN benefit_type = 'Health' AND coverage_level = 'Standard' THEN 250
            WHEN benefit_type = 'Health' AND coverage_level = 'Premium' THEN 400
            WHEN benefit_type = 'Health' AND coverage_level = 'Family' THEN 600
            WHEN benefit_type = 'Dental' AND coverage_level = 'Basic' THEN 25
            WHEN benefit_type = 'Dental' AND coverage_level = 'Standard' THEN 45
            WHEN benefit_type = 'Vision' THEN 15
            WHEN benefit_type = 'Life' THEN 20
            WHEN benefit_type = 'Disability' THEN 30
            WHEN benefit_type = 'Retirement' THEN 0  -- Company contribution, no employee cost
            ELSE 0
        END
    ),
    
    -- Date logic: end date must be after start date if specified
    CHECK (end_date IS NULL OR end_date > start_date),
    
    -- Prevent duplicate benefit types for same employee in overlapping periods
    UNIQUE (employee_id, benefit_type, start_date),
    
    FOREIGN KEY (employee_id) REFERENCES employees(employee_id) ON DELETE CASCADE
);
```

## Chapter 7: Transactions and Data Safety

Understanding transactions is like understanding the difference between rough drafts and final publications. A transaction groups multiple database operations together so they either all succeed as a complete unit, or if anything goes wrong, the entire group is undone. This prevents your database from getting stuck in an inconsistent state where some changes were applied but others weren't.

Think of it like transferring money between bank accounts. You wouldn't want a situation where money is deducted from one account but never added to the other because of a system error. Transactions ensure that either both operations complete successfully, or neither happens at all.

```sql
-- Complex transaction example: Student registration process
BEGIN IMMEDIATE TRANSACTION;

-- First, verify the student exists and is in good standing
SELECT student_id, academic_status 
FROM students 
WHERE student_id = 12345 AND academic_status NOT IN ('Suspended', 'Expelled');

-- Check if course has available capacity
SELECT max_enrollment, 
       (SELECT COUNT(*) FROM enrollments WHERE course_id = 301) as current_enrollment
FROM courses 
WHERE course_id = 301 AND is_active = 1;

-- If validation passes, proceed with registration
INSERT INTO enrollments (student_id, course_id, semester, enrollment_date)
VALUES (12345, 301, 'Fall 2024', date('now'));

-- Update course statistics
UPDATE courses 
SET current_enrollment = current_enrollment + 1
WHERE course_id = 301;

-- Record the transaction in audit log
INSERT INTO registration_audit_log (student_id, course_id, action, timestamp)
VALUES (12345, 301, 'ENROLLED', datetime('now'));

-- Update student's total credit hours
UPDATE students 
SET total_credits = total_credits + (
    SELECT credits FROM courses WHERE course_id = 301
)
WHERE student_id = 12345;

-- If all operations succeeded, commit the transaction
COMMIT;

-- If there was an error anywhere, the transaction would be rolled back automatically
-- You can also explicitly rollback: ROLLBACK;
```

### Advanced Transaction Patterns

SQLite supports different transaction modes that give you control over how concurrent access is handled. Understanding these modes helps you balance data consistency with system performance.

```sql
-- DEFERRED transaction (default): lock acquired when first read/write happens
BEGIN DEFERRED TRANSACTION;
-- Good for: Most general-purpose transactions

-- IMMEDIATE transaction: exclusive lock acquired immediately
BEGIN IMMEDIATE TRANSACTION;
-- Good for: When you know you'll be writing and want to avoid lock conflicts

-- EXCLUSIVE transaction: prevents all other database access
BEGIN EXCLUSIVE TRANSACTION;
-- Good for: Critical operations that need complete database consistency
```

```sql
        (item_type = 'Audiobook' AND format IN ('CD', 'Digital', 'Cassette')) OR
        (item_type = 'E-book' AND format IN ('PDF', 'EPUB', 'MOBI')) OR
        (item_type = 'Magazine' AND format IN ('Print', 'Digital')) OR
        (item_type = 'DVD' AND format = 'DVD') OR
        (item_type = 'Journal' AND format IN ('Print', 'Digital'))
    ),
    
    -- Page count validation (only for books and magazines)
    CHECK (
        (item_type IN ('Book', 'Magazine', 'Journal') AND page_count > 0) OR
        (item_type NOT IN ('Book', 'Magazine', 'Journal') AND page_count IS NULL)
    ),
    
    -- Cost validation
    CHECK (cost IS NULL OR cost >= 0),
    CHECK (replacement_cost IS NULL OR replacement_cost >= 0),
    
    -- Condition validation
    CHECK (condition_status IN ('Excellent', 'Good', 'Fair', 'Poor', 'Damaged')),
    
    FOREIGN KEY (publisher_id) REFERENCES publishers(publisher_id) ON DELETE SET NULL,
    FOREIGN KEY (category_id) REFERENCES categories(category_id) ON DELETE SET NULL
);

-- Junction table for many-to-many relationship between items and authors
CREATE TABLE item_authors (
    item_id INTEGER NOT NULL,
    author_id INTEGER NOT NULL,
    author_role TEXT DEFAULT 'Author',
    
    CHECK (author_role IN ('Author', 'Co-Author', 'Editor', 'Translator', 'Illustrator')),
    
    PRIMARY KEY (item_id, author_id, author_role),
    FOREIGN KEY (item_id) REFERENCES items(item_id) ON DELETE CASCADE,
    FOREIGN KEY (author_id) REFERENCES authors(author_id) ON DELETE CASCADE
);

-- Loans table: tracks who has borrowed what
CREATE TABLE loans (
    loan_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    item_id INTEGER NOT NULL,
    loan_date DATE DEFAULT (date('now')),
    due_date DATE NOT NULL,
    return_date DATE,
    renewal_count INTEGER DEFAULT 0,
    fine_amount REAL DEFAULT 0,
    status TEXT DEFAULT 'Active',
    
    -- Due date must be after loan date
    CHECK (due_date > loan_date),
    
    -- Return date must be after loan date if specified
    CHECK (return_date IS NULL OR return_date >= loan_date),
    
    -- Renewal count validation
    CHECK (renewal_count >= 0 AND renewal_count <= 3),
    
    -- Fine amount validation
    CHECK (fine_amount >= 0),
    
    -- Status validation
    CHECK (status IN ('Active', 'Returned', 'Overdue', 'Lost')),
    
    -- Status consistency: returned items must have return date
    CHECK (
        (status = 'Returned' AND return_date IS NOT NULL) OR
        (status != 'Returned')
    ),
    
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE RESTRICT,
    FOREIGN KEY (item_id) REFERENCES items(item_id) ON DELETE RESTRICT
);

-- Reservations table: holds for items that are currently checked out
CREATE TABLE reservations (
    reservation_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    item_id INTEGER NOT NULL,
    reservation_date DATE DEFAULT (date('now')),
    expiration_date DATE NOT NULL,
    status TEXT DEFAULT 'Active',
    notification_sent BOOLEAN DEFAULT 0,
    
    -- Expiration must be after reservation date
    CHECK (expiration_date > reservation_date),
    
    -- Status validation
    CHECK (status IN ('Active', 'Fulfilled', 'Expired', 'Cancelled')),
    
    -- Prevent duplicate active reservations
    UNIQUE (user_id, item_id, status) WHERE status = 'Active',
    
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    FOREIGN KEY (item_id) REFERENCES items(item_id) ON DELETE CASCADE
);

-- Fine payments tracking
CREATE TABLE fine_payments (
    payment_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    loan_id INTEGER,
    amount REAL NOT NULL CHECK (amount > 0),
    payment_date DATE DEFAULT (date('now')),
    payment_method TEXT NOT NULL,
    transaction_reference TEXT,
    
    CHECK (payment_method IN ('Cash', 'Credit Card', 'Debit Card', 'Check', 'Online')),
    
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE RESTRICT,
    FOREIGN KEY (loan_id) REFERENCES loans(loan_id) ON DELETE SET NULL
);
```

```sql
        MAX(l.loan_date) as last_loan_date,
        -- Calculate return on investment
        CASE 
            WHEN COUNT(l.loan_id) > 0 AND i.cost > 0

)

    authors,
    category,

    acquisition_date,

    condition_status,
    total_loans,
    loans_last_year,
    loans_last_6_months,
    last_loan_date,
    roi_ratio,
    -- Decision recommendation
    CASE 
        WHEN condition_status = 'Poor' OR condition_status = 'Damaged' 
        THEN 'RETIRE - Poor Condition'
        WHEN years_in_collection > 5 AND loans_last_year = 0 
        THEN 'RETIRE - No Recent Interest'
        WHEN loans_last_6_months = 0 AND years_in_collection > 2 
        THEN 'REVIEW - Low Activity'
        WHEN roi_ratio > 3 AND loans_last_6_months > 0 
        THEN 'ACQUIRE MORE - High Demand'
        WHEN loans_last_year >= 10 
        THEN 'ACQUIRE MORE - Popular'
        ELSE 'KEEP - Adequate Performance'
    END as recommendation,
    -- Priority score for decision making
    CASE 
        WHEN condition_status IN ('Poor', 'Damaged') THEN 100
        WHEN years_in_collection > 5 AND loans_last_year = 0 THEN 90
        WHEN roi_ratio > 5 THEN 10  -- High value items get low priority (keep them)
        WHEN loans_last_year >= 15 THEN 5
        ELSE 50
    END as action_priority
FROM item_performance
WHERE recommendation NOT LIKE 'KEEP%'
ORDER BY action_priority DESC, roi_ratio DESC;
```

## Teaching Strategies and Assessment Guidelines

### Progressive Complexity Approach

When teaching this material, start with the conceptual foundations before introducing syntax. Help students understand that databases are about modeling real-world relationships and enforcing business rules, not just storing data. Each constraint and relationship they define should solve a specific business problem.

Begin with simple single-table queries and gradually introduce joins, subqueries, and advanced features. The library example works well because students can relate to the domain and understand why certain rules exist (why books have due dates, why there are limits on renewals, etc.).

### Common Student Misconceptions to Address

Students often struggle with NULL handling, thinking NULL equals zero or empty string. Demonstrate how NULL propagates through expressions and why special handling is needed. Show examples of how `COUNT(*)` differs from `COUNT(column_name)` when NULLs are present.

Another common issue is confusion between WHERE and HAVING clauses. Use concrete examples to show that WHERE filters individual rows before grouping, while HAVING filters groups after aggregation. The library fines example works well here - you might want to find users with overdue books (WHERE) versus finding users whose total fines exceed $10 (HAVING).

### Assessment Ideas

Create scenarios where students must design database schemas for different domains (restaurant management, social media platform, inventory system) and write queries to answer specific business questions. Focus on having them explain their design decisions and justify their constraint choices.

For advanced students, include performance optimization challenges where they must identify bottlenecks and create appropriate indexes. The library system provides excellent opportunities for this - searching for books by title, finding overdue loans, generating usage reports.

### Extensions for Advanced Learning

Once students master the basics, introduce topics like database normalization theory, ACID properties, concurrency control, and backup strategies. The practical exercise can be extended to include user authentication, audit logging, and integration with external systems.

Consider having students build simple applications that interact with their database, which reinforces the importance of proper constraint design and helps them understand how database design impacts application development.

The key is maintaining the balance between theoretical understanding and practical application, always connecting abstract concepts to real-world problems that students can understand and relate to. This approach helps them not just memorize SQL syntax, but truly understand how to think about data and solve problems with relational databases.

```sql
-- Challenge 3A: Market Basket Analysis

        cp1.genre as genre_1,
        cp2.genre as genre_2,

        AVG(cp1.tracks_in_genre + cp2.tracks_in_genre) as avg_tracks_combined
    FROM customer_purchases cp1
    JOIN customer_purchases cp2 ON cp1.CustomerId = cp2.CustomerId
    WHERE cp1.genre < cp2.genre  -- Prevent duplicate pairs and self-pairs
    GROUP BY cp1.genre, cp2.genre
    HAVING customers_buying_both >= 3  -- Focus on meaningful patterns
)

    -- Calculate what percentage of genre_1 buyers also buy genre_2

        customers_buying_both * 100.0 / 
        (SELECT COUNT(DISTINCT CustomerId) FROM customer_purchases WHERE genre = genre_1),
        1
    ) as cross_purchase_rate
FROM genre_combinations
ORDER BY customers_buying_both DESC, cross_purchase_rate DESC;
```

### Common Student Mistakes to Address

Students often struggle with the difference between WHERE and HAVING. Remember that WHERE filters individual rows before grouping, while HAVING filters groups after aggregation.

Another common confusion is with NULL values. NULL is not the same as zero or an empty string - it represents missing or unknown data. Teach students that most operations with NULL result in NULL, and they need special handling with IS NULL and IS NOT NULL.
