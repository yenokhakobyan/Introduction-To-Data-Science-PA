## 1. Model Architecture Parameters

These parameters define the model's structure and are fixed after training.

### 1.1 Parameters (Weights)

**What it is**: The learnable values (weights and biases) in the neural network. When we say "7B model," we mean 7 billion parameters.

**Impact**: More parameters = more capacity to learn patterns = better performance (generally)

```
┌─────────────────────────────────────────────────────────────────┐
│                    WHERE PARAMETERS LIVE                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Input: "The cat sat on the"                                    │
│              │                                                  │
│              ▼                                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  EMBEDDING LAYER                                        │   │
│  │  Parameters: vocab_size × hidden_dim                    │   │
│  │  Example: 128,000 × 4,096 = 524M parameters            │   │
│  └─────────────────────────────────────────────────────────┘   │
│              │                                                  │
│              ▼                                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  TRANSFORMER LAYERS (×32 layers)                        │   │
│  │  Each layer contains:                                   │   │
│  │  • Attention weights: 4 × (hidden² ) = 67M params      │   │
│  │  • FFN weights: 8 × hidden² = 134M params              │   │
│  │  Total per layer: ~200M parameters                      │   │
│  └─────────────────────────────────────────────────────────┘   │
│              │                                                  │
│              ▼                                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  OUTPUT LAYER                                           │   │
│  │  Parameters: hidden_dim × vocab_size                    │   │
│  │  (Often tied with embeddings)                           │   │
│  └─────────────────────────────────────────────────────────┘   │
│              │                                                  │
│              ▼                                                  │
│  Output: "mat" (predicted next token)                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Model size comparison**:

| Model | Parameters | Memory (FP16) | Typical Use |
|-------|------------|---------------|-------------|
| 1B | 1 billion | ~2 GB | Edge devices, simple tasks |
| 7B | 7 billion | ~14 GB | Consumer GPUs, general use |
| 70B | 70 billion | ~140 GB | Production, complex reasoning |
| 405B | 405 billion | ~810 GB | State-of-the-art, research |

### 1.2 Context Window (Sequence Length)

**What it is**: Maximum number of tokens the model can process at once (input + output combined).

**Impact**: Larger context = can handle longer documents, but requires more memory and computation (quadratic scaling with standard attention).

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     CONTEXT WINDOW EXAMPLE                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Model: 4,096 token context window                                      │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐ │
│  │ Token 1    Token 2    Token 3   ...   Token 4094  Token 4095  4096│ │
│  │ "The"      "quick"    "brown"   ...   "jumped"    "over"     "the"│ │
│  └───────────────────────────────────────────────────────────────────┘ │
│  ◄──────────────────── Context Window ─────────────────────────────────►│
│                                                                         │
│  WHAT FITS IN DIFFERENT CONTEXT SIZES:                                  │
│                                                                         │
│  • 4K tokens   ≈ 3,000 words    ≈ 6 pages                              │
│  • 8K tokens   ≈ 6,000 words    ≈ 12 pages                             │
│  • 32K tokens  ≈ 24,000 words   ≈ 50 pages (short novel)               │
│  • 128K tokens ≈ 96,000 words   ≈ 200 pages                            │
│  • 200K tokens ≈ 150,000 words  ≈ 300+ pages (full novel)              │
│  • 1M tokens   ≈ 750,000 words  ≈ multiple books                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Real-world example**:

```
INPUT (within context):
─────────────────────────────────────────────────────────
"In Chapter 1, John moved to Paris. 
 In Chapter 2, he met Marie at a café.
 In Chapter 3, they discussed philosophy.
 ...
 [50 pages of story]
 ...
 In Chapter 20, John reflected on his journey.
 
 Question: Where did John first meet Marie?"
─────────────────────────────────────────────────────────

✅ With 128K context: "John met Marie at a café in Paris (Chapter 2)"
❌ With 4K context: Can't see Chapter 2, will fail or hallucinate
```

### 1.3 Hidden Dimension (d_model)

**What it is**: The size of the vector representing each token internally.

**Impact**: Larger hidden dim = richer representations = captures more nuance

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     HIDDEN DIMENSION VISUALIZATION                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Token: "bank"                                                          │
│                                                                         │
│  Small hidden dim (256):                                                │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ [0.2, -0.5, 0.8, ..., 0.1]  (256 numbers)                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Can encode: financial institution OR river bank                      │
│  → Struggles with subtle meanings                                       │
│                                                                         │
│  Large hidden dim (4096):                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ [0.2, -0.5, 0.8, 0.3, -0.1, ..., 0.7, -0.2, 0.1]  (4096 numbers)│   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Can encode: financial bank, river bank, bank shot (pool),           │
│    memory bank, blood bank, food bank, bank angle (aviation)...        │
│  → Captures subtle contextual differences                               │
│                                                                         │
│  Example sentences (same word, different meanings):                     │
│                                                                         │
│  "I deposited money at the bank"     → financial meaning activated     │
│  "We had a picnic on the river bank" → geographical meaning activated  │
│  "She made an incredible bank shot"  → sports meaning activated        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical values**:

| Model Size | Hidden Dimension |
|------------|------------------|
| 1B | 2,048 |
| 7B | 4,096 |
| 70B | 8,192 |
| 405B | 16,384 |

### 1.4 Number of Layers (Depth)

**What it is**: How many transformer blocks are stacked. Each layer refines the representation.

**Impact**: More layers = deeper reasoning and abstraction

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    WHAT EACH LAYER LEARNS                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Input: "The doctor said she would call the patient tomorrow"           │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  LAYER 1-4: Surface features                                    │   │
│  │  • Word boundaries                                              │   │
│  │  • Basic syntax                                                 │   │
│  │  • "she" is a pronoun                                           │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  LAYER 5-12: Syntactic understanding                            │   │
│  │  • Sentence structure                                           │   │
│  │  • "she" refers to "doctor" (not patient)                       │   │
│  │  • "tomorrow" modifies "call"                                   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  LAYER 13-24: Semantic understanding                            │   │
│  │  • Medical context established                                  │   │
│  │  • Professional relationship understood                         │   │
│  │  • Future action implied                                        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  LAYER 25-32: Complex reasoning                                 │   │
│  │  • Can answer: "Who will make the call?" → The doctor           │   │
│  │  • Can infer: The patient is waiting for results                │   │
│  │  • Can reason: This is a follow-up appointment scenario         │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical values**:

| Model Size | Layers |
|------------|--------|
| 1B | 16-24 |
| 7B | 32 |
| 70B | 80 |
| 405B | 126 |

### 1.5 Attention Heads (Multi-Head Attention)

**What it is**: Parallel attention mechanisms that can focus on different aspects of the input simultaneously.

**Impact**: More heads = can track more relationships at once

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    MULTI-HEAD ATTENTION EXAMPLE                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Sentence: "The cat that the dog chased ran up the tree"                │
│                                                                         │
│  Different attention heads focus on different relationships:            │
│                                                                         │
│  HEAD 1 (Subject-Verb):                                                 │
│  "The cat that the dog chased ran up the tree"                          │
│       ███                       ███                                     │
│       └───────────────────────────┘                                     │
│       cat ←──────────────────→ ran                                      │
│                                                                         │
│  HEAD 2 (Relative Clause):                                              │
│  "The cat that the dog chased ran up the tree"                          │
│       ███ ████                                                          │
│       └─────┘                                                           │
│       cat ← that (relative pronoun refers to cat)                       │
│                                                                         │
│  HEAD 3 (Object-Verb in subclause):                                     │
│  "The cat that the dog chased ran up the tree"                          │
│                   ███ ██████                                            │
│                   └─────┘                                               │
│                   dog → chased (dog is doing the chasing)               │
│                                                                         │
│  HEAD 4 (Prepositional Attachment):                                     │
│  "The cat that the dog chased ran up the tree"                          │
│                                 ███ ██ ███ ████                         │
│                                 └────────────┘                          │
│                                 ran → up the tree                       │
│                                                                         │
│  Combined: Model understands the full meaning:                          │
│  "A cat (which was being chased by a dog) ran up a tree"               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical values**:

| Model Size | Attention Heads | Head Dimension |
|------------|-----------------|----------------|
| 7B | 32 | 128 |
| 70B | 64 | 128 |
| 405B | 128 | 128 |

### 1.6 Vocabulary Size

**What it is**: Number of unique tokens the model knows.

**Impact**: Larger vocab = fewer tokens needed to represent text = more efficient, but larger embedding tables.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TOKENIZATION COMPARISON                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Text: "unhappiness"                                                    │
│                                                                         │
│  SMALL VOCABULARY (10K tokens):                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  "un" + "ha" + "pp" + "ine" + "ss" = 5 tokens                   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → More tokens needed                                                   │
│  → Loses morphological structure                                        │
│                                                                         │
│  MEDIUM VOCABULARY (32K tokens):                                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  "un" + "happiness" = 2 tokens                                  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Captures prefix meaning                                              │
│  → More efficient                                                       │
│                                                                         │
│  LARGE VOCABULARY (128K tokens):                                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  "unhappiness" = 1 token                                        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Most efficient                                                       │
│  → Word treated as atomic unit                                          │
│                                                                         │
│  ─────────────────────────────────────────────────────────────────────  │
│                                                                         │
│  MULTILINGUAL EXAMPLE: "こんにちは" (Hello in Japanese)                 │
│                                                                         │
│  English-focused vocab: "こ" + "ん" + "に" + "ち" + "は" = 5 tokens    │
│  Multilingual vocab:    "こんにちは" = 1-2 tokens                       │
│                                                                         │
│  → Affects efficiency for non-English languages!                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 2. Training Parameters

These control how the model learns during training.

### 2.1 Learning Rate

**What it is**: How big of a step to take when updating weights.

**Impact**: Too high = unstable training, too low = slow convergence

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    LEARNING RATE IMPACT                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Goal: Find the lowest point (optimal weights)                          │
│                                                                         │
│  Loss                                                                   │
│    │                                                                    │
│    │   ╭─╮                                                              │
│    │  ╱   ╲           TOO HIGH (lr=1e-2)                               │
│    │ ╱     ╲    ×──×     Overshoots, unstable                          │
│    │╱       ╲ ×    ×                                                    │
│    │         ╳      ×──×                                                │
│    │        ╱ ╲          ╲                                              │
│    │       ╱   ╲          Diverges!                                     │
│    │      ╱     ╲                                                       │
│    │     ╱   ●   ╲   JUST RIGHT (lr=3e-4)                              │
│    │    ╱    │●   ╲    Converges smoothly                              │
│    │   ╱      │●   ╲     │                                             │
│    │  ╱        │●───●────●  Found minimum!                             │
│    │ ╱          ╲                                                       │
│    │╱   ○────○───○────○────○   TOO LOW (lr=1e-6)                       │
│    │                           Very slow progress                       │
│    └────────────────────────────────────────────────── Training Steps  │
│                                                                         │
│  TYPICAL SCHEDULES:                                                     │
│                                                                         │
│  Learning Rate                                                          │
│    │                                                                    │
│    │    ╭───╮                                                           │
│    │   ╱     ╲                                                          │
│    │  ╱       ╲              Cosine decay with warmup                  │
│    │ ╱         ╲             (most common for LLMs)                    │
│    │╱           ╲                                                       │
│    │  Warmup     ╲─────────                                            │
│    └─────────────────────────────────────────────── Training Steps     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical values**:
- Pre-training: 1e-4 to 3e-4
- Fine-tuning: 1e-5 to 5e-5
- LoRA: 1e-4 to 3e-4

---

### 2.2 Batch Size

**What it is**: Number of examples processed before updating weights.

**Impact**: Larger batch = more stable gradients, but needs more memory

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    BATCH SIZE EXPLAINED                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Training data: 1 million sentences                                     │
│                                                                         │
│  BATCH SIZE = 1 (Stochastic Gradient Descent):                         │
│  ┌──────────────────────────────────────────────────────────┐          │
│  │ Sentence 1: "The cat sat" → Calculate loss → Update      │          │
│  │ Sentence 2: "Dogs bark"   → Calculate loss → Update      │          │
│  │ Sentence 3: "I love AI"   → Calculate loss → Update      │          │
│  │ ...                                                      │          │
│  │ 1 million updates per epoch                              │          │
│  └──────────────────────────────────────────────────────────┘          │
│  ✗ Very noisy gradients                                                 │
│  ✗ Slow (can't parallelize)                                            │
│  ✓ Low memory                                                          │
│                                                                         │
│  BATCH SIZE = 32:                                                       │
│  ┌──────────────────────────────────────────────────────────┐          │
│  │ Sentences 1-32:  → Average loss → Single update          │          │
│  │ Sentences 33-64: → Average loss → Single update          │          │
│  │ ...                                                      │          │
│  │ ~31,250 updates per epoch                                │          │
│  └──────────────────────────────────────────────────────────┘          │
│  ✓ Smoother gradients                                                  │
│  ✓ Can use GPU parallelism                                             │
│  ✗ More memory                                                         │
│                                                                         │
│  BATCH SIZE = 4,000,000 tokens (LLM pre-training):                     │
│  ┌──────────────────────────────────────────────────────────┐          │
│  │ Process 4M tokens → Very stable gradient → Update        │          │
│  │ (Uses gradient accumulation across many GPUs)            │          │
│  └──────────────────────────────────────────────────────────┘          │
│  ✓ Very stable training                                                │
│  ✓ Efficient hardware utilization                                      │
│  ✗ Requires distributed training                                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.3 Dropout

**What it is**: Randomly "drops" (zeros out) neurons during training to prevent overfitting.

**Impact**: Acts as regularization, makes model more robust

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    DROPOUT VISUALIZATION                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  WITHOUT DROPOUT:                                                       │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Input: "The quick brown fox"                                   │   │
│  │                                                                 │   │
│  │      ●────●────●────●────●                                      │   │
│  │      │╲  ╱│╲  ╱│╲  ╱│╲  ╱│    All neurons active               │   │
│  │      ●────●────●────●────●    Every training step              │   │
│  │      │╲  ╱│╲  ╱│╲  ╱│╲  ╱│                                      │   │
│  │      ●────●────●────●────●                                      │   │
│  │                                                                 │   │
│  │  Problem: Model memorizes training data (overfitting)           │   │
│  │  "The quick brown fox" → Always predicts "jumps"                │   │
│  │  But fails on: "The fast brown fox" → ???                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  WITH DROPOUT (p=0.1, 10% dropped):                                    │
│                                                                         │
│  Training Step 1:                Training Step 2:                       │
│  ┌─────────────────────────┐    ┌─────────────────────────┐            │
│  │  ●────●────○────●────●  │    │  ●────○────●────●────●  │            │
│  │  │╲  ╱│    │╲  ╱│╲  ╱│  │    │  │    │╲  ╱│╲  ╱│╲  ╱│  │            │
│  │  ●────●────●────○────●  │    │  ●────●────●────●────○  │            │
│  │  │╲  ╱│╲  ╱│    │╲  ╱│  │    │  │╲  ╱│╲  ╱│╲  ╱│    │  │            │
│  │  ○────●────●────●────●  │    │  ●────●────○────●────●  │            │
│  │                         │    │                         │            │
│  │  ○ = dropped neuron     │    │  Different neurons      │            │
│  └─────────────────────────┘    └─────────────────────────┘            │
│                                                                         │
│  Result: Model learns robust features that don't rely on any           │
│  single neuron → Generalizes better to new inputs!                     │
│                                                                         │
│  "The quick brown fox" → "jumps" ✓                                     │
│  "The fast brown fox"  → "jumps" ✓ (generalizes!)                      │
│                                                                         │
│  NOTE: Dropout is DISABLED during inference (all neurons active)       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical values**:
- Attention dropout: 0.0 - 0.1
- Hidden dropout: 0.0 - 0.1
- Modern LLMs often use 0 dropout (rely on other regularization)

### 2.4 Weight Decay

**What it is**: Penalizes large weights to prevent overfitting.

**Impact**: Keeps weights small, improves generalization

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    WEIGHT DECAY EFFECT                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Loss = Prediction_Loss + λ × Σ(weights²)                              │
│                           ↑                                             │
│                     Weight decay term                                   │
│                                                                         │
│  WITHOUT WEIGHT DECAY (λ=0):                                           │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Weights can grow arbitrarily large:                            │   │
│  │  w₁ = 1000, w₂ = -500, w₃ = 2000                                │   │
│  │                                                                 │   │
│  │  Model becomes sensitive to tiny input changes                  │   │
│  │  Input: 0.001 × 1000 = 1.0 (huge impact!)                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  WITH WEIGHT DECAY (λ=0.1):                                            │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Large weights are penalized:                                   │   │
│  │  w₁ = 0.5, w₂ = -0.3, w₃ = 0.8                                  │   │
│  │                                                                 │   │
│  │  Model is more stable                                           │   │
│  │  Input: 0.001 × 0.5 = 0.0005 (proportional impact)              │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Typical value for LLMs: 0.01 - 0.1                                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. Inference Parameters

These control how the model generates text. **You can adjust these at runtime!**

### 3.1 Temperature

**What it is**: Controls randomness in token selection. Scales the logits before softmax.

**Impact**: Higher = more creative/random, Lower = more focused/deterministic

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TEMPERATURE EFFECT ON OUTPUT                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Prompt: "The best programming language is"                             │
│                                                                         │
│  Raw logits from model (before temperature):                            │
│  ┌───────────────────────────────────────┐                             │
│  │ "Python": 5.0                         │                             │
│  │ "JavaScript": 4.2                     │                             │
│  │ "Java": 3.8                           │                             │
│  │ "C++": 3.5                            │                             │
│  │ "Rust": 3.2                           │                             │
│  │ "banana": 0.1                         │                             │
│  └───────────────────────────────────────┘                             │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════   │
│                                                                         │
│  TEMPERATURE = 0.0 (Greedy/Deterministic):                             │
│  ┌───────────────────────────────────────┐                             │
│  │ "Python":     ████████████████ 100%   │  Always picks highest      │

### 3.2 Top-p (Nucleus Sampling)

**What it is**: Only consider tokens whose cumulative probability reaches p.

**Impact**: Dynamically adjusts the candidate pool based on confidence

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TOP-P (NUCLEUS SAMPLING)                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Prompt: "The capital of France is"                                     │
│                                                                         │
│  Probability distribution:                                              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Paris":     ██████████████████████████████████████████  85%    │   │
│  │ "the":       ████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   8%    │   │
│  │ "a":         ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   4%    │   │
│  │ "located":   █░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   2%    │   │
│  │ "Lyon":      ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ 0.5%    │   │
│  │ "banana":    ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ 0.01%   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  TOP-P = 0.9 (90% cumulative probability):                             │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Cumulative: 85% ──► 93% ──► 97%                                 │   │
│  │             Paris    +the   +a                                  │   │
│  │                      ↑                                          │   │
│  │                   Stop here! 93% > 90%                          │   │
│  │                                                                 │   │
│  │ Only consider: ["Paris", "the"]                                 │   │
│  │ "a", "located", "Lyon", "banana" are excluded                   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════   │
│                                                                         │
│  WHY IS THIS USEFUL? It adapts to model confidence!                    │
│                                                                         │
│  HIGH CONFIDENCE (factual):                                            │
│  "2 + 2 ="                                                             │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "4": 99.9%  ← top-p=0.9 means only "4" is considered            │   │
│  │ "four": 0.05%                                                   │   │
│  │ "5": 0.01%                                                      │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Very focused, correct answer guaranteed                             │
│                                                                         │
│  LOW CONFIDENCE (creative):                                            │
│  "The dragon's name was"                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Smaug": 15%   }                                                │   │
│  │ "Draco": 12%   }                                                │   │
│  │ "Fire": 10%    } ← top-p=0.9 includes many options              │   │
│  │ "the": 8%      }                                                │   │
│  │ "ancient": 7%  }                                                │   │
│  │ ...            }                                                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → More options, allows creativity                                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Typical value**: 0.9 - 0.95

### 3.3 Top-k

**What it is**: Only consider the k most likely tokens.

**Impact**: Hard cutoff on number of candidates

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TOP-K SAMPLING                                       │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Prompt: "My favorite color is"                                         │
│                                                                         │
│  All token probabilities:                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 1. "blue":   25%                                                │   │
│  │ 2. "red":    20%                                                │   │
│  │ 3. "green":  15%                                                │   │
│  │ 4. "purple": 10%                                                │   │
│  │ 5. "yellow":  8%                                                │   │
│  │ 6. "orange":  6%                                                │   │
│  │ 7. "pink":    5%                                                │   │
│  │ 8. "black":   4%                                                │   │
│  │ 9. "white":   3%                                                │   │
│  │ 10. "the":    2%                                                │   │
│  │ ...                                                             │   │
│  │ 1000. "banana": 0.0001%                                         │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  TOP-K = 5:                                                            │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Only consider top 5:                                            │   │
│  │ "blue", "red", "green", "purple", "yellow"                      │   │
│  │                                                                 │   │
│  │ Renormalized probabilities:                                     │   │
│  │ "blue":   32%  (25/78)                                          │   │
│  │ "red":    26%  (20/78)                                          │   │
│  │ "green":  19%  (15/78)                                          │   │
│  │ "purple": 13%  (10/78)                                          │   │
│  │ "yellow": 10%  (8/78)                                           │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  TOP-K = 1 (same as greedy/temp=0):                                    │
│  Only "blue" is ever selected                                          │
│                                                                         │
│  TOP-K = 50 (common default):                                          │
│  Allows for reasonable variety while excluding unlikely tokens         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Top-k vs Top-p**:

| Aspect | Top-k | Top-p |
|--------|-------|-------|
| Cutoff type | Fixed number | Dynamic by probability |
| Adapts to confidence | No | Yes |
| Best for | Consistent variety | Adaptive generation |

### 3.4 Max Tokens

**What it is**: Maximum number of tokens the model will generate.

**Impact**: Controls response length, prevents runaway generation

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    MAX TOKENS EXAMPLES                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Prompt: "Explain quantum computing"                                    │
│                                                                         │
│  MAX_TOKENS = 50:                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Quantum computing uses quantum bits (qubits) that can exist   │   │
│  │ in multiple states simultaneously, unlike classical bits.      │   │
│  │ This enables parallel processing of many possibilities..."     │   │
│  │                                              [TRUNCATED]        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Brief, may cut off mid-thought                                      │
│                                                                         │
│  MAX_TOKENS = 500:                                                     │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Quantum computing uses quantum bits (qubits) that can exist   │   │
│  │ in multiple states simultaneously, unlike classical bits...    │   │
│  │                                                                 │   │
│  │ [Full explanation with examples, applications, current state   │   │
│  │ of the technology, comparison to classical computing...]       │   │
│  │                                                                 │   │
│  │ In summary, quantum computing represents a paradigm shift..."  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  → Complete, thorough response                                         │
│                                                                         │
│  IMPORTANT: max_tokens ≠ guaranteed length                             │
│  Model may stop earlier if it reaches a natural endpoint (EOS token)   │
│                                                                         │
│  Context window constraint:                                            │
│  input_tokens + max_tokens ≤ context_window                            │
│                                                                         │
│  Example: 128K context, 100K input tokens                              │
│  → Max possible output: 28K tokens                                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.5 Stop Sequences

**What it is**: Strings that trigger the model to stop generating.

**Impact**: Control where generation ends

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    STOP SEQUENCES                                       │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  WITHOUT STOP SEQUENCES:                                               │
│                                                                         │
│  Prompt: "User: What's 2+2?\nAssistant:"                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "The answer is 4.                                               │   │
│  │                                                                 │   │
│  │ User: That's correct! What about 3+3?                           │   │
│  │                                                                 │   │
│  │ Assistant: 3+3 equals 6.                                        │   │
│  │                                                                 │   │
│  │ User: Great! And 10+10?"                                        │   │
│  │ ...                                                             │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  ↑ Model hallucinates an entire fake conversation!                     │
│                                                                         │
│  WITH STOP SEQUENCES: ["\nUser:", "\n\n"]                              │
│                                                                         │
│  Prompt: "User: What's 2+2?\nAssistant:"                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "The answer is 4."                                              │   │
│  │                                    [STOPPED at "\nUser:"]       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  ↑ Clean, single response                                              │
│                                                                         │
│  COMMON STOP SEQUENCES:                                                │

│  • "```" - End of code block                                           │

│  • "Human:" / "User:" - Prevent role-playing continuation              │
│  • "[END]" - Custom end marker                                         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.6 Presence & Frequency Penalty

**What it is**: Penalties to reduce repetition.

**Impact**: Encourages diversity in generated text

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    REPETITION PENALTIES                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  WITHOUT PENALTIES:                                                    │
│  Prompt: "Write about the benefits of exercise"                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Exercise is good for health. Exercise helps you stay fit.     │   │
│  │ Exercise improves your mood. Exercise is important. Exercise   │   │
│  │ can help with weight loss. Exercise is beneficial..."          │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  ↑ Repetitive and boring!                                              │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════   │
│                                                                         │
│  PRESENCE PENALTY (0.0 to 2.0):                                        │
│  Penalizes tokens that have appeared AT ALL                            │
│                                                                         │
│  Token "exercise" appeared → Apply penalty regardless of count         │
│                                                                         │
│  presence_penalty = 1.0:                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Exercise is good for health. Physical activity helps you      │   │
│  │ stay fit. Working out improves your mood. Regular movement     │   │
│  │ is important. Training can help with weight loss..."           │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  ↑ Uses synonyms, more varied vocabulary                               │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════   │
│                                                                         │
│  FREQUENCY PENALTY (0.0 to 2.0):                                       │
│  Penalizes tokens proportional to HOW OFTEN they appeared              │
│                                                                         │
│  "the" appeared 5 times → Penalty = 5 × frequency_penalty              │
│  "exercise" appeared 2 times → Penalty = 2 × frequency_penalty         │
│                                                                         │
│  frequency_penalty = 0.5:                                              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ "Exercise is beneficial for health. It helps you stay fit,     │   │
│  │ improves mood, supports weight management, and builds          │   │
│  │ strength. Regular physical activity also boosts energy..."     │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│  ↑ Naturally flowing, avoids over-repetition                           │
│                                                                         │
│  RECOMMENDED VALUES:                                                   │
│  • Creative writing: presence=0.5-1.0, frequency=0.3-0.7              │
│  • Factual/technical: presence=0.0-0.3, frequency=0.0-0.3             │
│  • Code generation: presence=0.0, frequency=0.0 (repetition OK)        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 0. Terminology & Definitions

This section provides clear definitions for all key concepts used throughout this guide.

### 0.1 Core Architecture Terms

| Term | Definition | Example/Analogy |
|------|------------|-----------------|
| **Transformer** | A neural network architecture that uses self-attention mechanisms to process sequential data in parallel, replacing older recurrent approaches. Introduced in "Attention Is All You Need" (2017). | Like reading a book where you can see all pages at once and understand how every word relates to every other word, rather than reading one word at a time. |
| **Attention Mechanism** | A technique that allows the model to focus on different parts of the input when producing each part of the output. Computes relevance scores between all pairs of positions. | Like highlighting the most relevant words in a document when answering a specific question. |
| **Self-Attention** | A specific type of attention where the model relates different positions within the same sequence to compute a representation. Each token attends to all other tokens. | When reading "The cat sat on the mat because it was tired," self-attention helps the model understand "it" refers to "cat." |
| **Multi-Head Attention** | Running multiple attention operations in parallel, each learning different types of relationships (syntax, semantics, coreference, etc.). | Like having multiple experts each looking for different patterns in the same text simultaneously. |

### 0.2 Model Architecture Types

| Term | Definition | How It Works | Best Use Cases |
|------|------------|--------------|----------------|
| **Decoder-Only** | Architecture that generates text one token at a time, where each token can only attend to previous tokens (causal/left-to-right attention). The model predicts "what comes next." | Input: "The cat sat" → Model predicts: "on" → Then predicts: "the" → etc. Each prediction only sees what came before. | Text generation, chatbots, code completion, creative writing |
| **Encoder-Only** | Architecture that processes the entire input bidirectionally (each token can attend to all other tokens). Produces contextual representations but doesn't generate new text directly. | Input: "The bank by the river" → Each word gets a representation informed by ALL other words, so "bank" is understood as riverbank. | Text classification, named entity recognition, sentiment analysis, semantic search |
| **Encoder-Decoder** | Two-part architecture: encoder processes input bidirectionally to create representations, decoder generates output autoregressively while attending to encoder outputs. | Encoder: "Translate: Hello world" → [representations] → Decoder: "Bonjour" → "monde" | Translation, summarization, question answering |
| **Mixture of Experts (MoE)** | Architecture with multiple "expert" sub-networks, where a gating mechanism routes each input to only a subset of experts. Allows massive model capacity with lower compute cost. | A 400B parameter MoE might only activate 50B parameters per token, routing to 2 of 16 experts based on the input. | Large-scale models needing efficiency (Mixtral, Switch Transformer) |

### 0.3 Training & Learning Terms

| Term | Definition | Details |
|------|------------|---------|
| **Autoregressive** | A generation method where each output token is predicted based on all previous tokens. The model generates one token at a time, feeding each prediction back as input for the next. | P(text) = P(token₁) × P(token₂\|token₁) × P(token₃\|token₁,token₂) × ... |
| **Next-Token Prediction** | The fundamental training objective for decoder-only LLMs: given a sequence of tokens, predict the next token. Trained on massive text corpora. | Training example: "The quick brown" → predict "fox" |
| **Pre-training** | The initial phase of training where the model learns general language understanding from massive unlabeled text corpora (trillions of tokens). Creates a "foundation model." | Like general education before specialization—learning grammar, facts, reasoning patterns from the internet. |
| **Fine-tuning** | Adapting a pre-trained model for specific tasks or behaviors by training on a smaller, targeted dataset. Modifies some or all model weights. | Teaching a general model to be a customer service agent using examples of good customer service conversations. |
| **Supervised Fine-Tuning (SFT)** | Fine-tuning using labeled examples of desired input-output pairs. For LLMs, typically instruction-response pairs. | Training data: {"instruction": "Summarize this article", "response": "The article discusses..."} |
| **Transfer Learning** | Using knowledge gained from one task (pre-training) to improve performance on another task (fine-tuning). The foundation of modern LLM training. | A model pre-trained on web text can transfer that knowledge to become a medical assistant with minimal additional training. |
| **Few-Shot Learning** | The model's ability to learn new tasks from just a few examples provided in the prompt, without any weight updates. | "Translate English to French: cat → chat, dog → chien, house → ?" |
| **Zero-Shot Learning** | Performing a task without any examples, relying purely on instruction understanding from pre-training. | "Translate 'hello' to French" without any translation examples. |
| **In-Context Learning (ICL)** | The ability to learn patterns from examples within the prompt context, adapting behavior without gradient updates. Emergent capability of large models. | Showing the model 3 examples of a specific format, and it generalizes to new inputs in that format. |

### 0.4 Alignment & RLHF Terms

| Term | Definition | Details |
|------|------------|---------|
| **Alignment** | The process of making AI systems behave in accordance with human intentions, values, and preferences. Ensuring the model is helpful, harmless, and honest. | A well-aligned model refuses harmful requests, admits uncertainty, and follows user intent. |
| **RLHF (Reinforcement Learning from Human Feedback)** | A training technique that uses human preferences to train a reward model, then optimizes the LLM policy using reinforcement learning to maximize that reward. | Humans rank outputs A > B → train reward model → use PPO to make LLM produce more A-like outputs. |
| **Reward Model** | A model trained to predict human preferences, outputting a scalar score for how "good" a response is. Used to guide RL training. | Input: (prompt, response) → Output: 0.85 (high quality) or 0.23 (low quality) |
| **PPO (Proximal Policy Optimization)** | A reinforcement learning algorithm that updates the policy (LLM) to maximize reward while staying close to the original policy. Prevents drastic changes that could destabilize training. | The "proximal" constraint ensures the model doesn't change too much in each update, improving stability. |
| **DPO (Direct Preference Optimization)** | A simpler alternative to RLHF that directly optimizes on preference pairs without training a separate reward model. Uses a clever mathematical reformulation. | Instead of: preferences → reward model → RL, DPO does: preferences → direct policy optimization. |
| **KTO (Kahneman-Tversky Optimization)** | An alignment method that only requires binary feedback (good/bad) rather than preference pairs. Based on prospect theory from behavioral economics. | Simpler data collection: just label outputs as 👍 or 👎 rather than comparing pairs. |
| **Constitutional AI (CAI)** | An alignment approach where the model critiques and revises its own outputs based on a set of principles ("constitution"), reducing need for human feedback. | Model generates response → self-critiques against principles → revises → repeat. |
| **KL Divergence** | A measure of how much one probability distribution differs from another. In RLHF, used to keep the fine-tuned model close to the original, preventing reward hacking. | A penalty term that says "don't stray too far from your pre-trained behavior." |

### 0.5 Parameter-Efficient Fine-Tuning (PEFT)

| Term | Definition | Details |
|------|------------|---------|
| **LoRA (Low-Rank Adaptation)** | A fine-tuning method that freezes original weights and adds small trainable "adapter" matrices. Decomposes weight updates into low-rank matrices, drastically reducing trainable parameters. | Instead of updating a 4096×4096 matrix (16M params), learn two matrices: 4096×16 and 16×4096 (131K params). |
| **Rank (r)** | In LoRA, the dimensionality of the low-rank decomposition. Lower rank = fewer parameters but less expressiveness. Typical values: 8-64. | r=16 means weight updates are approximated by multiplying two rank-16 matrices. |
| **QLoRA** | Combines LoRA with quantization: base model is loaded in 4-bit precision while LoRA adapters are trained in higher precision. Enables fine-tuning 70B models on single GPUs. | 70B model in 4-bit ≈ 35GB, fits on one 40GB GPU for fine-tuning. |
| **Prefix Tuning** | Adds learnable "virtual tokens" to the beginning of each layer's input, keeping all original weights frozen. The prefixes learn task-specific behavior. | Like adding a learnable preamble that steers model behavior without changing the model itself. |
| **Adapter Layers** | Small neural network modules inserted between transformer layers. Only adapters are trained; original layers are frozen. | Each adapter: down-project → nonlinearity → up-project, adding <1% new parameters. |

### 0.6 Optimization & Inference Terms

| Term | Definition | Details |
|------|------------|---------|
| **Quantization** | Reducing the numerical precision of model weights (e.g., from 16-bit to 4-bit). Reduces memory usage and speeds up inference with minimal quality loss. | FP16 (16-bit) → INT8 (8-bit) = 2× memory reduction. INT4 = 4× reduction. |
| **INT8/INT4** | Integer representations using 8 or 4 bits per value. More limited range than floating-point but much more memory-efficient. | INT8: values from -128 to 127. INT4: values from -8 to 7 (or 0-15 unsigned). |
| **NF4 (Normal Float 4)** | A 4-bit data type optimized for normally distributed neural network weights. Used in QLoRA. Better preserves information than naive INT4. | The 16 possible values are spaced to match the typical distribution of neural network weights. |
| **KV-Cache** | Storing the key and value tensors from attention computation to avoid recomputing them for previous tokens during generation. Essential for efficient autoregressive inference. | Without cache: regenerate attention for all N tokens at each step. With cache: only compute for new token. O(N) vs O(N²) per token. |
| **Paged Attention** | Memory management technique (from vLLM) that stores KV-cache in non-contiguous blocks, like OS virtual memory. Enables efficient handling of variable-length sequences. | Instead of pre-allocating max_length memory per request, dynamically allocate pages as needed. |
| **Speculative Decoding** | Using a smaller, faster "draft" model to propose multiple tokens, then verifying them in parallel with the main model. Speeds up inference when draft model is accurate. | Draft model proposes 5 tokens in 10ms, main model verifies all 5 in one forward pass (50ms) instead of 5 separate passes (250ms). |
| **Continuous Batching** | Dynamically adding new requests to a running batch as previous requests complete, maximizing GPU utilization. Unlike static batching, doesn't wait for longest request. | Request A finishes → immediately add waiting Request D to the batch, no idle time. |
| **Flash Attention** | An IO-aware attention algorithm that reduces memory reads/writes by fusing operations and using tiling. Faster and more memory-efficient than standard attention. | 2-4× speedup, enables longer context lengths by reducing memory from O(N²) to O(N). |
| **Tensor Parallelism** | Splitting individual layers across multiple GPUs, with each GPU computing part of each layer. Needed for models too large for one GPU. | A 4096-dim layer split across 4 GPUs: each computes 1024 dims, then results are combined. |
| **Pipeline Parallelism** | Splitting model layers sequentially across GPUs, with each GPU handling a subset of layers. Data flows through GPUs in a pipeline. | GPU1: layers 1-10, GPU2: layers 11-20, etc. Micro-batches flow through the pipeline. |
| **FSDP (Fully Sharded Data Parallelism)** | Shards model parameters, gradients, and optimizer states across GPUs. Each GPU only stores a fraction of the full model, gathering weights as needed. | 70B model across 8 GPUs: each GPU stores ~9B parameters at rest, gathers full layers during forward/backward. |

### 0.7 RAG & Retrieval Terms

| Term | Definition | Details |
|------|------------|---------|
| **RAG (Retrieval-Augmented Generation)** | Enhancing LLM responses by first retrieving relevant documents from a knowledge base and including them in the context. Grounds responses in external knowledge. | User asks about company policy → retrieve relevant policy docs → LLM answers using those docs as context. |
| **Embedding** | A dense vector representation of text (or other data) in a high-dimensional space where semantic similarity corresponds to vector proximity. | "king" and "monarch" have similar embeddings; "king" and "banana" have dissimilar embeddings. |
| **Vector Database** | A database optimized for storing and querying high-dimensional vectors using similarity search (nearest neighbors). | Store 1M document embeddings, query "find 10 most similar to this query embedding" in milliseconds. |
| **Semantic Search** | Finding documents based on meaning rather than keyword matching. Uses embeddings to find semantically similar content. | Query "automobile" matches documents about "cars" and "vehicles" even without those exact words. |
| **Dense Retrieval** | Retrieval using learned embeddings (dense vectors). Both query and documents are embedded, and similarity is computed in embedding space. | Encode query → find nearest document embeddings → return those documents. |
| **Sparse Retrieval** | Traditional retrieval using term frequency statistics (like TF-IDF or BM25). Vectors are sparse (mostly zeros) with values for present terms. | BM25: score documents by weighted term overlap with query. Efficient and interpretable. |
| **Hybrid Search** | Combining dense (semantic) and sparse (keyword) retrieval to get benefits of both. Usually merged using reciprocal rank fusion or learned weights. | BM25 finds exact term matches; dense retrieval finds semantic matches; combine for best results. |
| **Reranking** | A second-stage scoring step that reorders initial retrieval results using a more expensive model (cross-encoder) for better precision. | Retrieve 100 docs with bi-encoder, rerank to top 10 with cross-encoder that sees query-doc pairs together. |
| **Cross-Encoder** | A model that takes a query-document pair as joint input and outputs a relevance score. More accurate than bi-encoders but slower (can't pre-compute). | Input: "[CLS] query [SEP] document" → Output: 0.92 relevance score. |
| **Bi-Encoder** | Encodes query and document separately into embeddings, then computes similarity (dot product/cosine). Enables pre-computing document embeddings. | Embed docs once → store in vector DB → at query time, only embed query and search. Fast but less accurate than cross-encoder. |
| **Chunking** | Splitting documents into smaller pieces for indexing and retrieval. Necessary because embeddings work best on shorter text and context windows are limited. | Split 50-page PDF into 500-token chunks with overlap, index each chunk separately. |

### 0.8 Prompting Terms

| Term | Definition | Details |
|------|------------|---------|
| **Prompt Engineering** | The practice of crafting input prompts to elicit desired outputs from LLMs. Includes formatting, examples, instructions, and constraints. | Adding "Let's think step by step" can improve reasoning accuracy by 10-20%. |
| **System Prompt** | Instructions that define the model's behavior, role, and constraints. Usually hidden from end users and persists across the conversation. | "You are a helpful coding assistant. Always explain your code and follow best practices." |
| **Chain-of-Thought (CoT)** | Prompting technique that encourages the model to show intermediate reasoning steps before giving a final answer. Improves performance on complex reasoning tasks. | "What is 23 × 17? Let's work through this step by step: 23 × 17 = 23 × 10 + 23 × 7 = 230 + 161 = 391" |
| **Tree of Thoughts (ToT)** | Extension of CoT that explores multiple reasoning paths, evaluates them, and can backtrack. Treats reasoning as search through a tree of possibilities. | Generate 3 possible next steps → evaluate each → expand the best ones → repeat. |
| **Self-Consistency** | Sampling multiple reasoning paths with temperature > 0, then taking the majority vote on final answers. Reduces variance from single samples. | Ask the same math problem 5 times → get answers: 42, 42, 41, 42, 42 → final answer: 42 (4/5 majority). |
| **ReAct (Reasoning + Acting)** | A prompting pattern that interleaves reasoning traces ("Thought: ...") with actions ("Action: search[query]") and observations. Foundation for tool-using agents. | Thought: I need current stock price → Action: search[AAPL stock price] → Observation: $185.50 → Thought: Now I can answer... |
| **Few-Shot Prompting** | Including examples of desired input-output behavior in the prompt to guide the model. | "Q: What's 2+2? A: 4\nQ: What's 3+5? A: 8\nQ: What's 7+9? A:" |
| **Prompt Caching** | Storing the processed representation of static prompt prefixes to avoid recomputation. Reduces cost and latency for repeated system prompts. | 10K token system prompt processed once → cached → subsequent requests skip those 10K tokens. |

### 0.9 Agent Terms

| Term | Definition | Details |
|------|------------|---------|
| **AI Agent** | An AI system that perceives its environment, reasons about goals, takes actions (often via tools), and learns from feedback. Goes beyond single-turn Q&A to multi-step task completion. | A coding agent that reads a bug report, searches codebase, edits files, runs tests, and submits a fix. |
| **Tool Use / Function Calling** | LLM capability to output structured calls to external tools/APIs rather than just text. Enables taking real-world actions. | Model outputs: {"function": "send_email", "args": {"to": "bob@example.com", "body": "..."}} |
| **Observation** | The result returned from executing a tool call or action. Fed back to the model for next reasoning step. | Action: search["weather NYC"] → Observation: "Currently 72°F and sunny in New York City" |
| **Planning** | The agent's ability to break complex tasks into subtasks, prioritize them, and create execution strategies. | Task: "Book me a trip to Paris" → Plan: 1) Find flight options, 2) Compare prices, 3) Check hotel availability, 4) Book best combination |
| **Memory (Agent Context)** | Information the agent maintains across interactions—short-term (conversation), long-term (vector store), episodic (past experiences). | Agent remembers user preferences from last week, retrieves relevant past task solutions, maintains current conversation context. |
| **Multi-Agent System** | Architecture with multiple specialized agents collaborating on complex tasks, each with different capabilities or perspectives. | Researcher agent gathers information → Analyst agent interprets → Writer agent produces report → Editor agent reviews. |
| **Reflection** | Agent capability to critique its own outputs and iteratively improve them. Meta-cognitive step that catches errors. | Generate answer → "Wait, I should verify this claim" → search for confirmation → revise answer if needed. |
| **Grounding** | Connecting model outputs to verifiable external sources or real-world data. Reduces hallucination through retrieval and citation. | Model claims "Company X has 10,000 employees" → grounded by citing recent SEC filing showing this number. |

### 0.10 Evaluation Terms

| Term | Definition | Details |
|------|------------|---------|
| **Perplexity** | A measure of how well a language model predicts a text. Lower perplexity = better predictions. Exponentiated average cross-entropy. | Perplexity of 10 means the model is as "surprised" by the text as if choosing from 10 equally likely words at each step. |
| **BLEU (Bilingual Evaluation Understudy)** | Metric comparing generated text to reference text by counting n-gram overlaps. Common in translation evaluation. | Measures precision: what fraction of generated n-grams appear in the reference? |
| **ROUGE (Recall-Oriented Understudy for Gisting Evaluation)** | Metrics for summarization comparing generated summaries to references. ROUGE-L measures longest common subsequence. | Measures recall: what fraction of reference n-grams appear in the generated text? |
| **LLM-as-Judge** | Using a (usually stronger) LLM to evaluate outputs of another LLM. Increasingly popular for nuanced quality assessment. | GPT-4 rates Claude's responses on helpfulness, accuracy, and clarity with scores and justifications. |
| **Benchmark** | Standardized test sets for evaluating model capabilities. Examples: MMLU (knowledge), HumanEval (coding), GSM8K (math). | MMLU: 57 subjects × 100+ questions = standardized comparison of model knowledge. |
| **Hallucination** | When an LLM generates plausible-sounding but factually incorrect or unsupported information. A major challenge for production systems. | Model confidently states a fake research paper title with made-up authors and wrong publication year. |
| **Latency** | Time to generate a response. Key metrics: TTFT (time to first token), throughput (tokens/second), end-to-end latency. | P50 latency: 200ms, P99 latency: 800ms (99th percentile is slowest 1% of requests). |

## 1. The LLM Landscape

### 1.1 Foundation Model Architectures

Modern LLMs are built on the **Transformer architecture** (Vaswani et al., 2017), with key innovations including:

> **Transformer**: A neural network architecture that uses self-attention to process sequences in parallel, enabling models to learn long-range dependencies efficiently. Replaced RNNs/LSTMs as the dominant architecture for NLP.

| Architecture Type | Key Models | Characteristics | How It Works |
|-------------------|------------|-----------------|--------------|
| **Decoder-only** | GPT-4, Claude, Llama 3, Gemini | Autoregressive, best for generation | Predicts one token at a time, each token only sees previous tokens (causal masking). Optimized for "what comes next?" |
| **Encoder-only** | BERT, RoBERTa | Bidirectional, best for understanding | Each token attends to all other tokens. Produces rich representations for classification, not generation. |
| **Encoder-Decoder** | T5, BART, Flan-UL2 | Sequence-to-sequence tasks | Encoder builds understanding of input; decoder generates output while attending to encoder states. Best for transformation tasks. |
| **Mixture of Experts (MoE)** | Mixtral, GPT-4 (speculated), DeepSeek | Sparse activation, efficiency gains | Routes each token to subset of "expert" sub-networks. 8× parameters but similar compute to dense model. |

### 1.2 Scaling Laws & Emergent Capabilities

> **Scaling Laws**: Mathematical relationships describing how model performance improves with increased compute, data, and parameters. Enable prediction of model capabilities before training.

The **Chinchilla scaling laws** established that **compute-optimal training** requires balancing model size with training tokens:

```
Optimal tokens ≈ 20 × model parameters
```

> **Compute-Optimal**: Training configuration that achieves the best performance for a given compute budget. Chinchilla showed previous models were undertrained (too few tokens relative to parameters).

**Emergent capabilities** appear at scale—abilities that are near-zero in smaller models but suddenly appear in larger ones:

| Emergent Capability | Definition | Approximate Threshold |
|---------------------|------------|----------------------|
| **Chain-of-thought reasoning** | Ability to solve problems by generating intermediate reasoning steps | ~100B parameters |
| **In-context learning** | Learning new tasks from examples in the prompt without weight updates | ~10B parameters |
| **Instruction following** | Understanding and executing natural language commands | ~1B parameters (with SFT) |
| **Tool use / function calling** | Generating structured outputs to invoke external APIs and tools | ~10B parameters (with training) |
| **Self-correction** | Identifying and fixing errors in own outputs when prompted | ~100B parameters |

## 2. AI Agents: Architecture & Design Patterns

### 2.1 What Defines an AI Agent?

> **AI Agent**: A system that uses an LLM as its core reasoning engine to autonomously perceive, plan, act, and learn in pursuit of goals. Unlike simple chatbots, agents take actions in the world and adapt based on feedback.

An AI agent is a system that uses an LLM as a **reasoning engine** to:

| Component | Definition | Example |
|-----------|------------|---------|
| **Perceive** | Gather information from the environment through tools, APIs, or sensors | Reading a database, browsing the web, receiving user messages |
| **Reason** | Analyze information, form plans, and decide on actions using the LLM | "I need flight info first, then hotel options, then I can compare" |
| **Act** | Execute actions through tool calls, API requests, or system commands | Calling a booking API, sending an email, writing a file |
| **Learn** | Improve through feedback, memory, and reflection on past actions | Storing successful strategies, avoiding past mistakes |

**Key distinction**: A chatbot responds to queries; an agent pursues goals through multi-step actions.

### 2.2 Core Agent Components

```
┌─────────────────────────────────────────────────────────────────┐
│                        AI AGENT SYSTEM                          │

### 2.3 Agent Design Patterns

#### Pattern 1: ReAct (Reasoning + Acting)

The foundational pattern interleaving reasoning traces with actions:

```python
class ReActAgent:
    def run(self, task: str) -> str:
        context = []
        while not self.is_complete(context):
            # Thought: Reason about what to do
            thought = self.llm.generate(
                f"Task: {task}\nContext: {context}\nThought:"
            )
            
            # Action: Decide on tool use
            action = self.llm.generate(
                f"Based on thought: {thought}\nAction:"
            )
            
            # Observation: Execute and observe
            observation = self.execute_tool(action)
            
            context.append({
                "thought": thought,
                "action": action,
                "observation": observation
            })
        
        return self.synthesize_answer(context)
```

#### Pattern 2: Plan-and-Execute

Separates planning from execution for complex multi-step tasks:

```python
class PlanExecuteAgent:
    def run(self, task: str) -> str:
        # Phase 1: Create high-level plan
        plan = self.planner.create_plan(task)  # List of subtasks
        
        # Phase 2: Execute each step
        results = []
        for step in plan:
            result = self.executor.execute(step, context=results)
            results.append(result)
            
            # Optional: Replan if needed
            if self.needs_replanning(results):
                plan = self.planner.replan(task, results)
        
        return self.synthesize(results)
```

#### Pattern 3: Multi-Agent Systems

Specialized agents collaborating on complex tasks:

```python
class MultiAgentOrchestrator:
    def __init__(self):
        self.agents = {
            "researcher": ResearchAgent(),
            "coder": CodingAgent(),
            "reviewer": ReviewAgent(),
            "writer": WritingAgent()
        }
    
    def solve(self, task: str) -> str:
        # Determine which agents to involve
        workflow = self.plan_workflow(task)
        
        state = {"task": task, "artifacts": {}}
        
        for step in workflow:
            agent = self.agents[step.agent_name]
            result = agent.execute(step.subtask, state)
            state["artifacts"][step.name] = result
        
        return state["artifacts"]["final_output"]
```

#### Pattern 4: Reflection & Self-Correction

Agents that critique and improve their outputs:

```python
class ReflectiveAgent:
    def run(self, task: str, max_iterations: int = 3) -> str:
        output = self.generate_initial(task)
        
        for i in range(max_iterations):
            # Self-critique
            critique = self.llm.generate(
                f"Task: {task}\n"
                f"Current output: {output}\n"
                "Critique this output. What's wrong or missing?"
            )
            
            if "looks good" in critique.lower():
                break
            
            # Refine based on critique
            output = self.llm.generate(
                f"Task: {task}\n"
                f"Previous output: {output}\n"
                f"Critique: {critique}\n"
                "Improved output:"
            )
        
        return output
```

### 2.5 Memory Systems

> **Agent Memory**: The mechanisms by which agents retain and retrieve information across interactions. Unlike stateless LLMs, agents with memory can learn from past experiences and maintain context over time.

| Memory Type | Definition | Implementation | Use Case |
|-------------|------------|----------------|----------|
| **Short-term** | Recent conversation context kept in the prompt | Conversation buffer | Maintaining dialogue coherence |
| **Long-term** | Persistent knowledge stored externally and retrieved as needed | Vector DB (Pinecone, Weaviate) | Facts, documents, past learnings |
| **Episodic** | Records of specific past experiences and their outcomes | Structured logs with retrieval | Learning from past task executions |
| **Semantic** | Conceptual knowledge organized by relationships | Knowledge graphs (Neo4j) | Entity relationships, ontologies |

```python
class HybridMemory:
    """
    Production memory system combining multiple memory types.
    
    - Short-term: Recent context, always included in prompt
    - Long-term: Large knowledge base, retrieved by relevance
    - Episodic: Past task executions for learning
    """
    def __init__(self):
        # Short-term: Last N tokens of conversation
        # Always included in context, provides immediate coherence
        self.short_term = ConversationBuffer(max_tokens=8000)
        
        # Long-term: Vector database for semantic retrieval
        # Query with embedding, get relevant past information
        self.long_term = VectorStore(embedding_model="text-embedding-3-large")
        
        # Episodic: Structured records of past task attempts
        # "Last time I tried X, Y happened, so I should Z"
        self.episodic = EpisodicMemory()
    
    def retrieve(self, query: str, k: int = 5) -> List[str]:
        """
        Combine memories with relevance weighting.
        Short-term is always included; long-term and episodic are retrieved.
        """
        short_term_context = self.short_term.get_recent()
        long_term_results = self.long_term.similarity_search(query, k=k)
        episodic_results = self.episodic.get_relevant_episodes(query)
        
        return self.rerank_and_merge(
            short_term_context, 
            long_term_results, 
            episodic_results
        )
```

### 3.1 Training Pipeline Overview

### 3.3 Supervised Fine-Tuning (SFT)

> **Supervised Fine-Tuning (SFT)**: Training a pre-trained model on labeled (instruction, response) pairs to teach it how to follow instructions and produce helpful outputs. Transforms a text-completion model into an assistant.

Transform base model into an instruction-following assistant:

**Data Format** (conversation style):
```json

    {"role": "system", "content": "You are a helpful assistant."},

    {"role": "assistant", "content": "Quantum computing uses quantum bits..."}
  ]

```

**Full Fine-Tuning vs. Parameter-Efficient Methods**:

> **Parameter-Efficient Fine-Tuning (PEFT)**: Methods that update only a small fraction of model parameters, dramatically reducing memory and compute requirements while maintaining most of the quality of full fine-tuning.

| Method | Definition | Memory | Trainable Params | Quality |
|--------|------------|--------|------------------|---------|
| **Full Fine-Tuning** | Update all model weights | ~16× model size | 100% | Best |
| **LoRA** | Add low-rank adapter matrices to attention layers; freeze original weights | ~1.1× model size | 0.1-1% | Near-full |
| **QLoRA** | LoRA with 4-bit quantized base model | ~0.5× model size | 0.1-1% | Good |
| **Prefix Tuning** | Learn virtual token embeddings prepended to each layer | ~1.05× model size | <0.1% | Moderate |

**LoRA Implementation**:

> **LoRA (Low-Rank Adaptation)**: Instead of updating a weight matrix W directly, LoRA adds a low-rank decomposition: W' = W + BA, where B and A are small matrices. If W is 4096×4096, and rank r=16, then B is 4096×16 and A is 16×4096—reducing trainable parameters from 16M to 131K.

### 3.4 Alignment: RLHF & Alternatives

> **Alignment**: The process of making AI systems behave in accordance with human values and intentions. An aligned model is helpful (does what users want), harmless (avoids causing harm), and honest (acknowledges uncertainty, doesn't deceive).

#### Reinforcement Learning from Human Feedback (RLHF)

> **RLHF**: A three-stage training process where: (1) humans compare model outputs to express preferences, (2) a reward model learns to predict these preferences, (3) the LLM is optimized via reinforcement learning to maximize the reward model's scores.

```
┌──────────────────────────────────────────────────────────────────┐
│                        RLHF PIPELINE                             │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Step 1: Collect Comparison Data                                 │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ Prompt → [Response A] vs [Response B] → Human ranks A > B  ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
│  Step 2: Train Reward Model                                      │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ RM(prompt, response) → scalar reward                        ││
│  │ Loss: -log(sigmoid(RM(preferred) - RM(rejected)))           ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
│  Step 3: Optimize Policy with PPO                                │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ Objective: E[RM(response)] - β·KL(π || π_ref)               ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**Key Components Explained**:

| Component | Definition | Purpose |
|-----------|------------|---------|
| **Reward Model (RM)** | A model trained to score responses based on human preferences | Provides training signal for RL |
| **PPO (Proximal Policy Optimization)** | An RL algorithm that updates the policy conservatively to maintain stability | Prevents drastic changes that could break the model |
| **KL Divergence Penalty** | A term that penalizes the model for straying too far from its original behavior | Prevents "reward hacking" and mode collapse |
| **Policy (π)** | The LLM's behavior—the probability distribution over outputs given inputs | What we're optimizing |

#### Direct Preference Optimization (DPO)

> **DPO**: A simpler alternative to RLHF that skips the reward model entirely. Uses a mathematical trick to directly optimize the policy on preference pairs, treating the LLM itself as an implicit reward model.

Simpler alternative that skips the reward model:

```python
def dpo_loss(
    policy_logprobs_chosen,
    policy_logprobs_rejected,
    ref_logprobs_chosen,
    ref_logprobs_rejected,
    beta=0.1
):
    """
    DPO directly optimizes the policy using preference pairs.
    No separate reward model needed.
    """
    chosen_rewards = beta * (policy_logprobs_chosen - ref_logprobs_chosen)
    rejected_rewards = beta * (policy_logprobs_rejected - ref_logprobs_rejected)
    
    loss = -F.logsigmoid(chosen_rewards - rejected_rewards).mean()
    return loss
```

**Comparison of Alignment Methods**:

| Method | Definition | Complexity | Stability | Compute | Results |
|--------|------------|------------|-----------|---------|---------|
| **RLHF (PPO)** | Full pipeline: reward model + reinforcement learning optimization | High | Challenging | 4× SFT | State-of-art |
| **DPO** | Direct optimization on preference pairs, no reward model | Medium | Stable | 2× SFT | Near RLHF |
| **KTO** | Uses binary (good/bad) feedback instead of preference pairs; based on prospect theory | Low | Very stable | 1.5× SFT | Good |
| **ORPO** | Combines SFT and preference optimization in a single step | Low | Stable | 1.5× SFT | Good |

#### Speculative Decoding

> **Speculative Decoding**: An inference acceleration technique where a small, fast "draft" model proposes multiple tokens, then the larger model verifies them all in one parallel forward pass. Achieves 2-3× speedup when draft accuracy is high.

```python
class SpeculativeDecoder:
    def __init__(self, main_model, draft_model, k=5):
        self.main = main_model
        self.draft = draft_model
        self.k = k  # Number of speculative tokens
    
    def generate(self, prompt, max_tokens):
        tokens = tokenize(prompt)
        
        while len(tokens) < max_tokens:
            # Draft model proposes k tokens
            draft_tokens = self.draft.generate(tokens, num_tokens=self.k)
            
            # Main model verifies in parallel
            main_logits = self.main.forward(tokens + draft_tokens)
            
            # Accept matching tokens, reject from first mismatch
            accepted = self.verify_and_accept(draft_tokens, main_logits)
            tokens.extend(accepted)
        
        return tokens
```

### 4.2 Prompt Engineering & Optimization

> **Prompt Engineering**: The practice of designing input prompts to elicit desired behaviors from LLMs. Includes structuring instructions, providing examples, and adding constraints. Often yields significant performance gains without any model changes.

#### Structured Prompting Techniques

```python
# Chain-of-Thought (CoT)
# Definition: A prompting technique that elicits step-by-step reasoning before the
# final answer. The reasoning "chain" helps the model work through complex problems.
# Adding "Let's think step by step" can improve accuracy by 10-40% on reasoning tasks.
cot_prompt = """
Solve this step by step:
Q: {question}

Let me work through this carefully:
Step 1: ...
"""

# Self-Consistency
# Definition: Sample multiple reasoning paths (with temperature > 0), extract the
# final answer from each, and take the majority vote. Reduces variance from
# single samples and improves accuracy on reasoning tasks.
def self_consistency(prompt, n_samples=5):
    responses = [llm.generate(prompt, temperature=0.7) for _ in range(n_samples)]
    answers = [extract_answer(r) for r in responses]
    return Counter(answers).most_common(1)[0][0]

# Tree of Thoughts (ToT)
# Definition: Extension of CoT that explores multiple reasoning branches at each step,
# evaluates them, and can backtrack. Treats reasoning as search through a tree of
# possible thought sequences. More powerful but more expensive than linear CoT.
def tree_of_thoughts(problem, breadth=3, depth=3):
    root = ThoughtNode(problem)
    for d in range(depth):
        for node in get_leaf_nodes(root):
            thoughts = generate_thoughts(node, n=breadth)
            evaluated = [(t, evaluate_thought(t)) for t in thoughts]
            best = sorted(evaluated, key=lambda x: x[1], reverse=True)[:2]
            node.children = [ThoughtNode(t) for t, _ in best]
    return get_best_path(root)
```

**Prompting Techniques Comparison**:

| Technique | Definition | When to Use | Cost |
|-----------|------------|-------------|------|
| **Zero-Shot** | Direct instruction with no examples | Simple tasks the model already understands | 1× |
| **Few-Shot** | Include examples of desired input→output behavior | Tasks needing specific format or style | 1.5-3× |
| **Chain-of-Thought** | Prompt model to show reasoning steps | Math, logic, multi-step reasoning | 2-5× |
| **Self-Consistency** | Sample multiple times, take majority vote | High-stakes reasoning where accuracy matters | 5-10× |
| **Tree of Thoughts** | Explore branching reasoning paths with backtracking | Complex planning and problem-solving | 20-50× |

### 4.3 RAG Optimization

> **RAG (Retrieval-Augmented Generation)**: A technique that enhances LLM responses by first retrieving relevant documents from a knowledge base and including them in the context. Enables the model to access up-to-date or proprietary information beyond its training data.

#### Advanced Retrieval Strategies

```python
class OptimizedRAG:
    """
    A production-ready RAG implementation with hybrid search and reranking.
    
    Key components:
    - Embedder (Bi-Encoder): Converts text to dense vectors for semantic search
    - Vector Store: Stores and indexes document embeddings for fast retrieval
    - Reranker (Cross-Encoder): More accurate but slower scoring of query-doc pairs
    """
    def __init__(self):
        # Bi-Encoder: Encode query and docs separately, compare via cosine similarity
        # Fast because docs can be pre-encoded, but less accurate than cross-encoder
        self.embedder = SentenceTransformer("BAAI/bge-large-en-v1.5")
        self.vector_store = Qdrant(...)
        
        # Cross-Encoder: Sees query and doc together, more accurate but can't pre-compute
        # Used for reranking a smaller candidate set
        self.reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")
    
    def retrieve(self, query: str, k: int = 20, final_k: int = 5) -> List[Document]:
        # Stage 1: Dense retrieval (fast, approximate)
        # Uses embedding similarity to find semantically related documents
        query_embedding = self.embedder.encode(query)
        candidates = self.vector_store.search(query_embedding, k=k)
        
        # Stage 2: Reranking (slower, more accurate)
        # Cross-encoder sees query and doc together for better relevance scoring
        pairs = [(query, doc.text) for doc in candidates]
        scores = self.reranker.predict(pairs)
        
        # Stage 3: Return top reranked results
        ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
        return [doc for doc, _ in ranked[:final_k]]
    
    def query(self, question: str) -> str:
        # Retrieve relevant context
        docs = self.retrieve(question)
        context = "\n\n".join([d.text for d in docs])
        
        # Generate with context - the LLM answers based on retrieved docs
        prompt = f"""Based on the following context, answer the question.

Context:
{context}

Question: {question}

Answer:"""
        
        return self.llm.generate(prompt)
```

#### Chunking Strategies

> **Chunking**: The process of splitting documents into smaller pieces for indexing and retrieval. Necessary because (1) embedding models have input limits, (2) embeddings work best on focused text, and (3) LLM context windows are limited.

| Strategy | Definition | Chunk Size | Overlap | Best For |
|----------|------------|------------|---------|----------|
| **Fixed** | Split by token/character count regardless of content | 512 tokens | 50 tokens | General documents |
| **Semantic** | Split at natural boundaries (sentences, paragraphs) to preserve meaning | Variable | Sentence boundary | Technical docs |
| **Hierarchical** | Create parent summaries with child detail chunks; retrieve child, include parent | Parent/child | Linked | Long documents |
| **Late Chunking** | Embed full document, then create chunk representations from the full-doc embedding | Full doc → chunk embeddings | N/A | Context preservation |

### 5.4 Reliability & Error Handling

> **Reliability Engineering**: Designing systems to maintain correct operation despite failures. For LLM systems, this includes handling model timeouts, GPU failures, rate limits, and degraded responses gracefully.

```python
import tenacity
from circuitbreaker import circuit

class RobustLLMClient:
    """
    Production-grade LLM client with multiple reliability patterns.
    
    Key patterns:
    - Circuit Breaker: Stop calling a failing service temporarily
    - Retry with Backoff: Automatically retry transient failures
    - Fallback: Use backup model when primary fails
    """
    def __init__(self, primary_endpoint, fallback_endpoint):
        self.primary = primary_endpoint
        self.fallback = fallback_endpoint
    
    # Circuit Breaker: After 5 failures in a row, "open" the circuit
    # for 60 seconds, preventing further calls to failing service.
    # This prevents cascade failures and gives the service time to recover.
    @circuit(failure_threshold=5, recovery_timeout=60)
    
    # Retry with Exponential Backoff: If request fails, wait 1s, 2s, 4s...
    # before retrying. Helps with transient network issues and rate limits.
    @tenacity.retry(
        stop=tenacity.stop_after_attempt(3),
        wait=tenacity.wait_exponential(multiplier=1, min=1, max=10),
        retry=tenacity.retry_if_exception_type(TransientError)
    )
    async def generate(self, request):
        try:
            return await self._call_primary(request)
        except CircuitBreakerOpen:
            # Fallback: When primary is down, use secondary model/endpoint
            # Might be smaller/cheaper model, but keeps service available
            return await self._call_fallback(request)
    
    async def _call_primary(self, request):
        async with aiohttp.ClientSession() as session:
            async with session.post(
                self.primary,
                json=request,
                timeout=aiohttp.ClientTimeout(total=30)
            ) as response:
                if response.status >= 500:
                    # Server errors are transient - retry
                    raise TransientError(f"Server error: {response.status}")
                return await response.json()
```

**Reliability Patterns Explained**:

| Pattern | Definition | When to Use |
|---------|------------|-------------|
| **Retry with Backoff** | Automatically retry failed requests with increasing delays | Transient network errors, rate limits |
| **Circuit Breaker** | Stop calling a failing service after N failures; retry after timeout | Prevent cascade failures, let services recover |
| **Fallback** | Use alternative (often degraded) response when primary fails | Maintain availability during outages |
| **Timeout** | Cancel requests that take too long | Prevent resource exhaustion, maintain latency SLAs |
| **Bulkhead** | Isolate failures to prevent them from affecting the whole system | Critical path protection |
| **Health Checks** | Regularly verify service availability | Load balancer routing, alerting |
```

### 5.5 Cost Optimization

> **Cost Optimization**: Strategies to reduce the computational and financial cost of running LLM systems while maintaining acceptable quality and latency.

| Strategy | Definition | Savings | Trade-off |
|----------|------------|---------|-----------|
| **Prompt caching** | Store processed representations of repeated prompt prefixes | 50-90% on repeated prefixes | None for cached content |
| **Batching** | Process multiple requests together to amortize GPU overhead | 30-50% throughput increase | Latency for individual requests |
| **Quantization** | Reduce numerical precision of model weights | 50-75% memory | 1-5% quality |
| **Smaller models** | Use capable smaller models for simpler tasks | 80-90% | Quality varies by task |
| **Semantic caching** | Cache responses to semantically similar (not just identical) queries | 40-70% on similar queries | Freshness, edge cases |

```python
class SemanticCache:
    """
    Cache responses to semantically similar queries, not just identical ones.
    
    How it works:
    1. Embed the query into a vector
    2. Search for similar queries in cache
    3. If similarity > threshold, return cached response
    4. Otherwise, generate new response and cache it
    
    Trade-off: Saves cost but may return stale or imprecise answers
    """
    def __init__(self, similarity_threshold=0.95):
        self.cache = {}  # query -> (embedding, response)
        self.embedder = SentenceTransformer("all-MiniLM-L6-v2")
        self.threshold = similarity_threshold  # How similar is "similar enough"?
    
    def get(self, query: str) -> Optional[str]:
        query_embedding = self.embedder.encode(query)
        
        for cached_query, (embedding, response) in self.cache.items():
            similarity = cosine_similarity(query_embedding, embedding)
            if similarity > self.threshold:
                return response  # Cache hit!
        return None  # Cache miss - need to generate
    
    def set(self, query: str, response: str):
        embedding = self.embedder.encode(query)
        self.cache[query] = (embedding, response)
```

| **Compute cost** | GPU_hours × hourly_rate | Quantization, batching |
| **Latency cost** | User drop-off due to slow responses | Smaller models, caching |
| **Quality cost** | Revenue impact of worse outputs | A/B test to find optimal trade-off |

class LLMEvaluator:
    """
    Comprehensive evaluation framework covering automated metrics,
    reference-based metrics, and LLM-as-judge approaches.
    """
    def __init__(self):
        self.metrics = {
            "factuality": FactualityChecker(),    # Checks claims against known facts
            "relevance": RelevanceScorer(),        # How well response addresses query
            "coherence": CoherenceScorer(),        # Logical flow and readability
            "safety": SafetyChecker(),             # Harmful content detection
            "latency": LatencyTracker(),           # Response time metrics
        }
    
    def evaluate(self, prompt, response, ground_truth=None):
        results = {}
        
        # Automated metrics (no reference needed)
        results["factuality"] = self.metrics["factuality"].score(response)
        results["coherence"] = self.metrics["coherence"].score(response)
        results["safety"] = self.metrics["safety"].check(response)
        
        # Reference-based metrics (require ground truth)
        # These compare generated output to known-correct outputs
        if ground_truth:
            results["relevance"] = self.metrics["relevance"].score(
                response, ground_truth
            )
            # BLEU: Measures n-gram precision (what % of generated n-grams are in reference)
            results["bleu"] = compute_bleu(response, ground_truth)
            # ROUGE: Measures n-gram recall (what % of reference n-grams are in generated)
            results["rouge"] = compute_rouge(response, ground_truth)
        
        # LLM-as-judge: Use a (usually stronger) LLM to evaluate responses
        # More nuanced than automated metrics, captures subjective quality
        results["llm_judge"] = self.llm_judge_score(prompt, response)
        
        return results
    
    def llm_judge_score(self, prompt, response):
        """
        LLM-as-Judge: Uses a capable LLM to rate response quality.
        More expensive but captures nuanced quality aspects that
        automated metrics miss.
        """
        judge_prompt = f"""
        Rate the following response on a scale of 1-10.
        
        User Query: {prompt}
        
        Response: {response}
        
        Criteria:
        - Helpfulness (1-10)
        - Accuracy (1-10)
        - Clarity (1-10)
        
        Provide scores in JSON format.
        """
        return self.judge_llm.generate(judge_prompt)
```

**Key Evaluation Metrics Explained**:

| Metric | Definition | Strengths | Weaknesses |
|--------|------------|-----------|------------|
| **Perplexity** | How "surprised" the model is by text; lower = better predictions | Fast, automatic | Doesn't measure downstream quality |
| **BLEU** | N-gram precision between generated and reference text | Standard for translation | Ignores meaning, requires references |
| **ROUGE** | N-gram recall between generated and reference text | Good for summarization | Ignores meaning, requires references |
| **LLM-as-Judge** | Using an LLM to evaluate another LLM's outputs | Captures nuance | Expensive, may have biases |
| **Human Evaluation** | Real humans rate quality, helpfulness, safety | Gold standard | Slow, expensive, subjective |
| **Hallucination Rate** | Percentage of claims that are unsupported/false | Measures factuality | Hard to automate accurately |

### 6.3 A/B Testing & Experimentation

> **A/B Testing**: Comparing two or more variants (models, prompts, parameters) by randomly assigning users to each variant and measuring outcome differences. Essential for data-driven decisions about model changes.

```python
class LLMExperiment:
    """
    Framework for running controlled A/B experiments on LLM variants.
    
    Key concepts:
    - Variant: Different versions being compared (control vs treatment)
    - Assignment: Consistently mapping users to variants
    - Statistical Significance: Confidence that observed differences are real
    """
    def __init__(self, experiment_name, variants):
        self.name = experiment_name
        self.variants = variants  # {"control": model_a, "treatment": model_b}
        self.results = defaultdict(list)
    
    def assign_variant(self, user_id: str) -> str:
        """
        Consistent hashing ensures same user always gets same variant.
        This is crucial for valid experiments - switching mid-experiment 
        would contaminate results.
        """
        hash_val = hash(f"{self.name}:{user_id}") % 100
        return "treatment" if hash_val < 50 else "control"
    
    async def run(self, user_id: str, request):
        variant = self.assign_variant(user_id)
        model = self.variants[variant]
        
        start = time.time()
        response = await model.generate(request)
        latency = time.time() - start
        
        # Record metrics for later analysis
        self.results[variant].append({
            "latency": latency,
            "tokens": response.usage.total_tokens,
            "user_rating": None  # Collected later via feedback
        })
        
        return response, variant
    
    def analyze(self):
        """
        Statistical analysis to determine if differences are significant.
        
        p-value < 0.05: 95% confident the difference is real, not random chance.
        """
        control_latencies = [r["latency"] for r in self.results["control"]]
        treatment_latencies = [r["latency"] for r in self.results["treatment"]]
        
        # t-test: Statistical test comparing means of two groups
        t_stat, p_value = stats.ttest_ind(control_latencies, treatment_latencies)
        
        return {
            "control_mean": np.mean(control_latencies),
            "treatment_mean": np.mean(treatment_latencies),
            "p_value": p_value,
            "significant": p_value < 0.05  # 95% confidence threshold
        }
```

| **Sample Size** | Number of observations needed for reliable conclusions | Too few = unreliable; too many = slow |
| **Holdout Group** | A control group that never sees changes | Baseline for comparison |
| **Metric Selection** | Choosing what to measure (latency, quality, user engagement) | Measure what you actually care about |

        dense_results = self.vector_store.similarity_search(query, k=k*2)
        
        # Sparse retrieval (BM25)
        sparse_results = self.bm25.search(query, k=k*2)
        
        # Merge and deduplicate
        all_results = self._reciprocal_rank_fusion(dense_results, sparse_results)
        
        # Rerank with cross-encoder
        pairs = [(query, chunk.text) for chunk in all_results[:k*2]]
        scores = self.reranker.predict(pairs)
        
        ranked = sorted(zip(all_results, scores), key=lambda x: x[1], reverse=True)
        return [chunk for chunk, _ in ranked[:k]]

# generator.py
class CitedAnswerGenerator:
    def __init__(self, llm_client):
        self.llm = llm_client
    
    async def generate(self, query: str, chunks: List[Chunk]) -> Answer:
        context = self._format_context(chunks)
        
        prompt = f"""Answer the question based on the provided context. 
Include citations in [1], [2] format referring to the source numbers.
If the answer cannot be found in the context, say so.

Context:
{context}

Question: {query}

Answer with citations:"""
        
        response = await self.llm.generate(prompt, stream=True)
        
        return Answer(
            text=response.text,
            citations=self._extract_citations(response.text, chunks),
            confidence=self._calculate_confidence(response, chunks)
        )

# agent.py
class ResearchAgent:
    def __init__(self, tools: ToolSuite, llm: LLMClient):
        self.tools = tools
        self.llm = llm
        self.memory = ResearchMemory()
        self.knowledge_graph = KnowledgeGraph()
    
    async def research(self, query: str, max_steps: int = 50) -> ResearchReport:
        # Create initial plan
        plan = await ResearchPlanner(self.llm).create_plan(query)
        self.memory.set_plan(plan)
        
        step = 0
        while step < max_steps and not self._is_complete():
            step += 1
            
            # Think: Decide what to do next
            thought = await self._think()
            
            # Act: Execute the decided action
            action, action_input = self._parse_action(thought)
            
            # Observe: Get and process results
            observation = await self._execute_action(action, action_input)
            
            # Update memory and knowledge
            self.memory.add_step(thought, action, observation)
            await self._update_knowledge(observation)
            
            # Check if replanning needed
            if self._needs_replanning():
                plan = await self._replan()
        
        # Generate final report
        return await self._generate_report()
    
    async def _think(self) -> str:
        context = self.memory.get_context()
        plan = self.memory.get_plan()
        progress = self.memory.get_progress()
        
        prompt = f"""You are a research agent working on this query:
{plan.main_question}

Current progress:
{progress}

Recent observations:
{context}

Remaining questions to answer:
{plan.get_remaining_questions()}

Available tools: {self.tools.get_tool_descriptions()}

Think about what to do next. Consider:
1. What information is still missing?
2. Which tool would help get that information?
3. How does this fit into the overall research plan?

Your response should be:
Thought: [Your reasoning]
Action: [tool_name]
Action Input: [input for the tool]
"""
        return await self.llm.generate(prompt)
    
    async def _execute_action(self, action: str, action_input: str) -> str:
        tool = self.tools.get(action)
        
        if action == "web_search":
            results = await tool.search(action_input)
            return self._format_search_results(results)
        
        elif action == "read_page":
            content = await tool.fetch(action_input)
            return self._extract_relevant_content(content)
        
        elif action == "run_python":
            result = await tool.execute(action_input)
            return result.output
        
        elif action == "take_note":
            self.memory.add_note(action_input)
            return "Note saved."
        
        elif action == "verify_fact":
            return await self._verify_fact(action_input)
    
    async def _verify_fact(self, claim: str) -> str:
        # Search for corroborating sources
        search_results = await self.tools.get("web_search").search(claim)
        
        # Check multiple sources
        verifications = []
        for result in search_results[:3]:
            content = await self.tools.get("read_page").fetch(result.url)
            verification = await self._check_claim_against_source(claim, content)
            verifications.append(verification)
        
        # Aggregate confidence
        confidence = sum(v.supports for v in verifications) / len(verifications)
        
        return f"Claim verification: {confidence:.0%} confidence based on {len(verifications)} sources"
    
    async def _generate_report(self) -> ResearchReport:
        knowledge = self.knowledge_graph.export()
        notes = self.memory.get_all_notes()
        sources = self.memory.get_all_sources()
        
        prompt = f"""Generate a comprehensive research report based on the following:

Research Question: {self.memory.get_plan().main_question}

Knowledge gathered:
{knowledge}

Key findings:
{notes}

Sources consulted:
{sources}

Create a report with:
1. Executive Summary
2. Methodology
3. Key Findings (with citations)
4. Analysis
5. Limitations
6. Conclusion
7. Bibliography

Use [1], [2] style citations.
"""
        
        report_text = await self.llm.generate(prompt)
        
        return ResearchReport(
            query=self.memory.get_plan().main_question,
            content=report_text,
            knowledge_graph=self.knowledge_graph,
            sources=sources,
            confidence_scores=self._calculate_confidence_scores(),
            methodology=self.memory.get_methodology_summary()
        )
